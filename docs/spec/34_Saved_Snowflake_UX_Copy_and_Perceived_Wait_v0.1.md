## 1. 기존 코드 확인과 문제

- `src/content/copy.ts`의 `savedMessage(theme,mode)`는 `growth|addition|complete`별 1문장만 반환. 실제 서로 다른 `entryDate` 수와 1~15일차 단계는 무관하다.
- `src/screens/App.tsx`: 저장 성공 뒤 `page.screen==='saved'`; `page.mode`, `previousWrittenDays`, `page.entryId`를 안다. 이때 `savedMessage(monthTheme,page.mode)`만 제목으로 렌더하며 실제 눈꽃은 `ArtworkSlot` `playback`으로 실행된다.
- `src/graphics/snowflake/SnowflakeArtwork.tsx`: `requestHistory(after,false)`로 1..15 prefix 스냅샷을 Worker에서 준비해 `hist`가 완료돼야 연출 시작. 과거 보고서 약 1.9s 준비 구간에서 **기존 14일차 눈꽃이 아무 변화 없이 보임**.
- 사용자 기대: 저장 성공은 즉시 확인돼야 하고, 그 사이에 앱이 멈춘 것처럼 보이지 않으며 이후 실제 과거 칭찬의 재성장과 눈결 보상이 자연스럽게 이어져야 한다. 시간을 숨기기 위한 **가짜 진척률, 사실과 다른 완료 선언**은 금지.

## 2. UX 라이팅 원칙

1. 한 문장 헤드라인, 짧은 확실한 완료 확인. 사용자의 성취를 칭찬하되 과장·어린아이 같은 의인화·과도한 시 감상은 피함.
2. `dayIndex`는 *해당 월 고유 `entryDate` 개수*. 같은 날 추가 일기는 일수 증가가 아니며 별도 카피. 전체 원문 `entries.length`는 꺼내보기 열림의 **10개 기준**으로 별도 계산.
3. 기록 날짜를 '어제'로 선택하거나 backfill해도 문구가 사실이 되도록 가능한 한 "오늘"이라는 시간 참조 피함. "7일 동안 연속" 같은 연속 기록 가정 절대 금지.
4. 구조에 대한 과장(실제 눈꽃에 없던 팔·끝 결정판 생성) 금지. 대부분 모티프가 형성되거나 밀도가 늘어나는 상태를 포괄하는 표현 사용.
5. 15일차는 `targetDays:15`인 **실제 상품 정책이 확정된 달**에서만 '완성' 사용. 2026-12 `targetDays:null`이면 15번째 distinct date라도 일반 성장 문구(아래 별도 안전 문구) 사용. 그 이후 16+에서도 목표 미확정이면 '완성'을 주장하지 않는다.
6. 기존 2027-01 sheep 및 theme 미설정 달은 눈꽃 카피와 분리. UI에 R3/I3, Gate, 'Worker', 글자 source identity, '캐시 생성 중' 같은 개발자 용어 노출 금지.
7. 접근성: 제목과 상태의 동시 갱신으로 screen reader가 다중 발화하지 않도록 live region 최소화, 움직임 줄이기에서는 짧은 완료 카피로 충분.

### 목표 달성 이후의 가변 문구 풀 [사용자 요청 반영 · 개별 문구는 제안]

**의도:** 목표 달성 순간은 한 번의 특별한 장면이고, 이후에도 기록하는 행위 자체가 기분 좋은 보상이 되도록 한다. 매번 "완성된 눈꽃"을 설명하지 말고 **나를 돌보는 말·따뜻함·다정함·인정**에 중심을 둔다. 모든 문구는 저장이 끝났음을 알리는 완료형이며, '오늘도', '매일', '연속', '15일' 등 backfill/중복 작성에서 사실과 다를 수 있는 말을 피한다. 눈꽃이 또 성장하거나 새로운 보상 모션이 재실행된다고 약속하지 않는다.

**문구 운영 정책:**

1. **실제 정책상 목표를 달성한 기록을 저장하는 순간에는 목표일 축하 헤드라인을 1회 표시한다.** 그다음 새 칭찬 저장부터 P01~P16 중 하나를 표시한다. 15일은 유력 후보이지만 아직 비즈니스 `targetDays` 확정 아님. `targetDays:null`에서는 목표 달성 카피를 절대로 노출하지 않는다.
2. 각 신규 저장 성공 **1건당 1개 문구를 선택해 해당 저장 이벤트에 고정**한다. 같은 저장 완료 화면을 다시 렌더하거나, 그래픽 로딩이 끝나거나, 뒤로 갔다 다시 들어와도 랜덤하게 문구가 바뀌지 않는다. 단순 브라우저 새로고침·리사이즈에서 다시 추첨하지 않는다.
3. 무작위 즉시 중복을 막기 위해 **shuffle-bag 순환(16개를 섞고 한 번씩 소진한 뒤 재셔플)** 또는 최근 4~5개 회피 방식을 검토. 문구 16개가 모두 한 번씩 노출되기 전에 특정 2~3개만 반복되지 않도록 한다. 서로 다른 날짜뿐 아니라 동일 날짜에 추가 작성한 칭찬에도 **저장 건마다** 다음 문구를 제공하되, 같은 날짜 추가에서는 눈꽃 성장 단계/complete 연출을 재발동하지 않는다.
4. **저장 성공 이전에 문구를 확정·표시하지 말 것.** 저장 실패 시 기존 오류 안내, 문구/랜덤 인덱스 변경 없음. 테스트용 fixture/실사용의 날짜 backfill/동일 일자 다중/수정/삭제에도 정확.
5. 재진입/리로드에 대한 안정성은 `entryId`별 저장 이벤트 선택 index와 재현 가능한 단순 순번/seed 사용. 개인 기록 `body`를 hash/seed/로그/analytics에 사용하지 않음. 기존 세션 `sessionStorage` 이외 영속 DB 도입 금지, 영구 선택 히스토리 저장은 데이터 모델 검토 후 결정.
6. **일반 저장 1줄 타이틀 중심**으로 표시. 매일 헤드라인의 길이·강조도·행 수를 지나치게 다르게 만들지 않는다. 서정적 은유를 두 개 이상 포개거나 너무 귀여운 장식적 표현/확인되지 않은 사용자 감정 단정은 피한다.
7. 꺼내보기 10개 해제가 동일 저장에서 발생한 경우 별도 최초 해제 안내를 중복 발화하지 않도록, 기존 1회 CTA/보조 메시지 정책을 우선한다.
8. [미정] 장기 누적 시 문구 풀 확장과 연속 방문 구분은 필요성을 보고 결정. 이 요구를 위한 일일 출석 streak/연속 작성 기능은 추가하지 않는다.

### 꺼내보기 동시 달성의 우선순위

- 꺼내보기는 `entries.length>=10`이면 최초 해제, once-unlocked이면 삭제 후에도 유지.
- `writtenDays==10`과 `entries.length==10`은 별개. 같은 날 두 편이면 10번째 칭찬은 다른 일차에 도달 가능.
- 최초 해제 안내: "칭찬 10개가 모였어요. 이제 하나씩 꺼내볼 수 있어요." (실제 저장이 10번째 **전체 칭찬**일 때에만 안내)
- 저장 후 눈꽃 제목과 동시에 2개 축하 토스트를 경쟁시키지 않음. 시각적으로는 눈꽃 제목 우선, 보조 1회 안내/가벼운 CTA로 표시하고 TalkBack/VoiceOver에서는 한 번 읽히도록 중복 live region 회피.

## 4. 지연 체감 개선: 속도를 숨기는 것이 아니라 '아무 일도 없는 화면'을 없애기

### 먼저 실제 시간 단축 (개발 우선)

1. `save confirmed`/작품 `historyReady`/첫 움직임 `firstVisualChange`/최종 I3 mount / `rewardStart` 시각 분리 측정. 지금 보고된 약 1.9초가 **단일 비트맵 생성 비용인지 15-prefix Worker waiting인지** 분리.
2. 사용자가 글을 쓰는 동안(저장 전) 이미 있는 이전 기록의 역사 prefix `S1..S14`는 백그라운드 Worker에서 **idle 시점**에 안전하게 prewarm 가능. 저장 전 새 원문/미래 상태 canvas를 시각 노출 금지. 사용자 타이핑 blocking, 개인 원문 telemetry/로그 저장 금지. 하드웨어 low-end와 긴 글에서도 측정.
3. 저장 성공 뒤 최종 `S15` 등 필요한 후속 상태만 계산, prefix가 이미 캐시되면 batch read. Promise.all 전체를 기다리는 방식 vs 단계별 결과 스트리밍(초기 rewind에 필요한 `S1` 먼저) 비교. 실제 stage endpoint의 3B R3/2I I3 parity 유지.
4. Worker 6초 timeout→main-thread 동기 fallback은 **장시간 프레임 정지 위험**. 사용자 피드백 표시 + 안정된 최종 작품 폴백/재시도와 취소 가능성 검토. "저장 실패"와 "연출 준비 지연" 구별.

| 준비가 계속되면 >0.4s | 14일 눈꽃의 원래 2.5D 움직임이 계속 보임; 짧고 작은 청백색 가장자리 반사 정도는 옵션. 화려한 빛·가짜 개화·위치 이동 금지 | **"지난 칭찬들이 모여 눈꽃을 피울 준비를 하고 있어요."** | 보조문구 1줄, 작은 무한 회전 아이콘/가짜 % 금지 |
| 실제 replay 시작 | 씨앗 되감기→성장→6개 팔 완성 | 기존 안내 문구 천천히 사라짐. 필요 시 "눈꽃이 다시 피어나고 있어요." | 자막이 주 연출보다 눈에 띄지 않게 |
| 완료 보상 종료 | I3 + 눈결, 완성 보상 뷰 | **정책 확정 시에만** "차곡차곡 모은 다정함이 하나의 눈꽃이 되었어요." | 2026-12 target null이면 "남긴 칭찬이 눈꽃에 더해졌어요." |

- 단, 14→15 준비 구간은 2026-12 검수 빌드에서만 실제 보상 재생. 실제 목표 미정이면 **완성 주장 금지**, 검수 안내는 테스트 전용.
- 보조문구의 가시성은 최소 약 0.6~0.8초 유지하거나, 빠르게 준비되면 등장하지 않도록 조정. 저장 확인·준비 안내·개화 안내가 0.3초 단위로 급변하는 것 금지.
- 원래 14일 작품이 살아 있는 동안 기존 I3 idle을 쓰는 것이 가장 정직함. 정지시킨 채 spinner만 띄우지 말 것. GPU 비싼 추가 입자는 준비 중 기본 OFF.
- 사용자에게 '기록이 저장되는 중'으로 거짓 말하지 않음. 저장 성공 뒤 역사 리플레이용 그래픽을 **준비**한다는 가벼운 서사만 사용.
- `prefers-reduced-motion`: 모션 없는 정적 완성형 + 즉시 완료 확인. 오래 걸리면 정적 "눈꽃을 준비하고 있어요."가 가능하지만 장식 애니메이션은 금지.
- 저장 완료 화면의 홈·다른 버튼은 장시간 7초 보상 전체를 강제로 기다리지 않도록. 화면 이탈 시 이벤트 클린업 및 한 번 재생 규칙 명시.

## 5. 추천 state/API 계약 (실제 코드 분석 후 이름 맞춤)

```ts
type SavedArtworkPhase =
  | 'saved'       // 데이터 저장 성공, 첫 프레임도 안정
  | 'preparing'   // 이전 prefix/새 최종 state 준비 중
  | 'replaying'   // 눈꽃 재성장 표시
  | 'rewarding'   // 스노우볼 효과
  | 'settled'     // I3 idle, event cleanup
  | 'artwork-fallback'; // 그래픽 실패지만 원문 저장은 성공
```

- `SavedScreen` headline: 저장 직후 "칭찬을 남겼어요." → 정적 완료 상태에서는 날짜 카피; 실제 15일 목표 달성이라면 보상 완성 시점으로 카피 전환. 보조 상태 line은 오래 준비되는 경우에만.
- 일기 body, 이력, title/referencePrompt는 카피 결정/로그에 사용하지 않음.
- `SavedScreen`-artifact의 상태는 **viewer callbacks**와 실제 Worker state 기반. 타이머가 2초 지났다고 무조건 `'replaying'`으로 바꾸는 가짜 진행 금지.
- `firstVisualChange`를 metrics 이벤트로 측정하되 제품 analytics로 raw diary/provenance/문구를 업로드하지 않음.
- 2027-01 Sheep은 기존 savedMessage를 유지하되 이후 별도의 월 테마 copy map으로 확장 가능. 범용 공용 문구를 snowflake로 덮지 말 것.

## 6. 필수 회귀/검수

- 저장 성공 시 앱 전체와 동작 일치, 실제 날짜 인덱스 1..15, 같은 날 2편, 16+, 과거 날짜 backfill, 다른 월 저장, 수정(새 성장 불가), 삭제, 0 entry.
- 10번째 칭찬/10번째 고유 작성일 분리, 이전 기록 해제 값 복구, 10번째 칭찬 저장 시 꺼내보기 1회 CTA/토스트.
- `targetDays:null`이거나 10·20인 경우 저장 카피가 가짜 15일 완성 문구를 출력하지 않음.
- 완료 이벤트 `saved`→`preparing`→`replaying`→`rewarding`→`settled`는 실제 진행과 일치. Worker 실패/6초 초과, 화면 이탈, StrictMode, reducedMotion, 돌아가기, 같은 save ID 중복 이벤트, 320/375/390/430px.
- 화면 리더 의미 확인, 200% 글자·키보드·iOS/Android WebView, 짧은/긴 신규 기록, sessionStorage 불안정/실패.
- 준비 지연의 실제 체감·선호는 사람의 시각 검수: 첫 0.5초에 안정적인 저장 확인이 보이는가? 2초 구간에서 멈춘 것처럼 보이지 않는가? 상태 안내가 너무 분주하지 않은가? 7초 애니메이션을 떠나기/건너뛰기가 가능한가?
