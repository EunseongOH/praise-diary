## 0. 이번 작업의 목적과 개발 범위

**목표**: "멀리서는 눈꽃, 가까이에서는 내가 쓴 말"을 **글자 자체가 이루는 2.5D 상징물**로 검증한다. 똑같은 가상 일기 데이터로 **A: 순수 문자형 2.5D**, **B: 최소 연결 획을 포함한 문자형 2.5D**를 나란히 만들어 동일 조건에서 시각적으로 비교한다.

**이번에 만드는 것**
- 개발 전용 A/B 비교 페이지(Playground): 1·5·8·15일 단계(0일 포함), 같은 날짜에 글 여러 편, 짧은/긴 일기, 1×/2×/3.2× 및 정지/미세 모션 비교.
- 2.5D 글자 조형, 연결된 문자 읽기 경로, 결정적 배치·성장 모델의 **독립 가능한 실험 엔진**.
- Playwright Test 자동 캡처/회귀 검사, 단위 테스트, 렌더링 성능 측정 및 보고서.
- 사용자 눈으로 고를 수 있게 A/B 비교 이미지와 미적 결함을 기록한 결과물.

**이번에 만들지 않는 것**
- 제품의 월간 눈꽃 구현 교체, 기존 홈·일기 작성·도감 UI 리디자인, 실제 로그인/서버 저장, 외부 공유 기능.
- 새로운 브랜드 색/폰트 최종 결정, 붉은 양·해의 전용 아트, 실제 12월 목표일 수 임의 확정.
- 사용자에게 확대 조작 버튼/배율 배지/온보딩 추가.
- 품질 보장을 가장한 임의 3D 라이브러리·고비용 WebGL 효과 도입.

**완료의 의미**: Playground와 테스트가 재현되고, 사용자가 A/B를 실제로 감상·비교할 수 있는 상태. A/B 중 어느 것을 최종 제품에 넣을지는 **별도의 디자인 승인 이후** 결정한다.

## 1. 바꾸면 안 되는 제품 원칙 [사용자 확정]

1. **글자 기반 작품**: 사용자가 남긴 실제 일기의 글자들이 눈꽃 형상을 만든다. AI 생성 문구·가짜 응원 문장·무의미한 영문 장식 금지.
2. **2.5D 입체감 필수**: 문자 전·중·후 레이어, 미세 깊이차, 겹침과 간접적인 원근감이 느껴져야 한다. 납작한 2D 글자 배열만 구현하면 불합격.
3. **조형과 독해의 동시 유지**: 정지된 1×에서는 눈꽃 형태가 인식되고, 2~3.2× 확대하면 같은 일기의 **실제 연속된 원문 일부**가 근처에서 연결되어 읽혀야 한다. 전체 원문을 아트에 우겨 넣지 않는다.
4. **아래에서 위로 성장**: 한 달의 서로 다른 작성일마다 1단계 성장. 같은 날짜의 추가 일기는 높이 증가 없이 열린 영역의 글자 밀도만 증가. 마지막 기록 삭제로 유일 작성일이 사라지면 작성일 수 감소.
5. **무경계 캔버스**: 아트 전용 카드·테두리·그림자·화려한 배경 그라데이션/글로우 없음. 현재 다크/팔레트는 임시로 동일 적용.
6. **확대는 선택 사항**: 실제 서비스에서는 기본 1×, 원하는 경우 핀치/팬. 확대 버튼·배율 표시·제스처 안내 문구 없음. Playground 내부 검사 패널에서는 배율 선택 허용.
7. **모션은 상징물 종속**: 큰 줄기, 세부 가지의 로컬 회전축; 개별 글자 무작위 떨림·광원 점멸·눈꽃 전체 무한 회전 금지. 사용자/OS 움직임 감소 모드에서는 반복 모션 정지.
8. **개인정보**: 데모는 가상 문장만 사용. 실제 일기 원문·글자 좌표·선택 구절을 테스트 리포트, 로그, 텔레메트리, 외부 공유 이미지에 기록하지 않는다.

## 2. 시안 A/B: 차이를 딱 하나로 제한 [디자인 실험]

| 구분 | A안 — 문자만으로 만든 2.5D 눈꽃 | B안 — 최소 연결 획 + 동일한 2.5D 눈꽃 |
|---|---|---|
| 핵심 재료 | 전경·중경·후경의 **실제 원문 글자**만 사용 | A안과 같은 글자/좌표/깊이 + 구조상 필요한 짧은 보조 획 |
| 실루엣 | 글자 밀도와 배열·반복으로 6중 결정 형성 | 글자 사이 접합부가 끊겨 보이는 곳에만 극소 연결 획 허용 |
| 추가 연결선 | **0개** | 전체 실루엣 윤곽 금지, 접합부당 최소한의 짧고 가는 선만(정량값 임시) |
| 깊이 / 2.5D | 필수 | A와 **동일 설정** |
| 텍스트 / 글자 위치 | A/B 완전히 동일 | A와 **동일** |
| 모션 / 색 / 서체 | A/B 완전히 동일 | A와 **동일** |

**통제 변수**: 화면 폭, DPR, 일기 데이터와 정렬, 글자 수, 공백/문장부호, `seed`, 성장 일수, 조도/색/대비, 서체, 글자 크기, 깊이(전·중·후 레이어 설정), 모션 위상, 캡처 시점은 전부 동일. 연결 획만 바꾸고 B안에 광채나 특별한 색/속도를 추가하지 않는다.

**판정 순서**: ① 모션 OFF 정지 상태의 눈꽃 인지성·형태 완성도 → ② 확대 시 글자 독해와 2.5D의 자연스러움 → ③ 모션 ON의 안정성·성능. 자동 스냅샷 일치 = 미적 승인이라는 주장은 금지.

## 3. 눈꽃 조형 및 2.5D 아트 모델 [실험 출발값 — 미확정]

### 3.1 기본 구조
- 시안 기준 좌표계 `viewBox="0 0 340 340"` 유지. 중심 1개, 60° 간격 큰 줄기 6개, 각 줄기에서 최대 3쌍 가지(현재 42개 그룹 출발). **형태를 검토하며 조정 가능하지만 A와 B에 동시에 반영**.
- 하단부터 자라는 영역은 `progress.ts`의 성장 규칙을 재사용. 아직 드러나지 않은 상단 윤곽·흐릿한 미완성 모양을 보여주지 않는다.
- 0일에는 눈꽃 부분을 출력하지 않는다. 1일에는 아래에 작은 조각, 5·8일에는 연결되는 부분, 완성 시에는 6중 구조가 확실히 읽히는 것을 의도한다.
- 중심부 너무 진한 뭉침, 화면 전체의 입자 구름화, 미세 글자 중복으로 만든 검은 얼룩, 바깥 가지의 끊김을 아트 결함으로 기록한다.

### 3.2 깊이층: 글자로 만든 두께

| 레이어 | 역할 | 글자 기반 조건 | 시안 조정값(확정 아님) |
|---|---|---|---|
| 후경(back) | 가지 뒤의 결/깊이·살짝 들어간 인상 | 사용자 실제 글자의 질감 레이어 | 인접 경로에서 ±1~3 SVG-unit 오프셋, 상대 농도 0.35~0.55 |
| 중경(mid) | 눈꽃의 구조와 볼륨의 중심 | 연결된 글자 경로, 밀도 균형 | 기본 경로·기본 크기, 상대 농도 0.60~0.85 |
| 전경(front) | 눈에 잘 보이는 글자의 가장자리/읽기 구간 | **실제 원문 순서를 보존한 가독 경로** | 기본 위치에서 소폭 앞으로, 상대 농도 0.85~1.0, 시안 크기 가산 0~8% |

- 2.5D는 **텍스트 레이어의 상대적 겹침, 크기·명도·오프셋, 미세한 차등 움직임**으로 구현. 반짝이는 겉재질·네온·유리·강한 그림자/블러 금지.
- 동일 일기 텍스트를 독해 레이어에서 중복 복제하여 두 문장처럼 보이게 하지 않는다. 후경의 글자 복제는 **읽기 대상이 아닌 질감**으로만 쓰고, 동일 글자임을 추적할 수 있어야 한다.
- 글자 자체가 각 층의 주된 시각 매체여야 하며, 눈꽃의 면을 별도 도형으로 채우고 그 위에 텍스트만 올리는 꼼수를 금지한다.
- 브라우저 성능 때문에 진짜 Z축 렌더링이 필요한 건 아니다. **SVG/2D 렌더 위 깊이 표현(시각적 2.5D)**부터 비교한다. WebGL/Three.js 도입은 프로파일 결과로 필요성이 입증될 때만 별도 승인 요청.
- 카메라 이동·대규모 패럴랙스는 기본 요구사항 아님. 모션 중 front/mid/back이 약간 다른 위상·폭으로 반응해도 텍스트 판독과 결정 실루엣이 무너지지 않아야 한다.

### 3.3 A/B 연결 획 정책
- B안에서만 접합부의 물리적 공백을 잇는 짧은 선을 배치. **전체 눈꽃의 선화가 먼저 존재하고 글자를 얹는 구조는 금지**.
- 연결선은 고정된 경로/로컬 좌표를 따르고, 아래→위 성장 마스크를 글자와 공유한다. 글자가 없는 곳에서 선만 단독으로 자라지 않는다.
- 연결 획 길이·굵기/불투명도는 Playground에서 **개발자만** 조정하되, A/B 정식 캡처에서는 고정값 사용. 제품에 사용자 조절 UI를 추가하지 않는다.

## 4. 글자 배치: 하나의 일기가 하나의 이어지는 흐름 [핵심]

### 4.1 모델
```
DiaryEntry → 순서가 보존된 원문/구절 → reading lane(연결된 경로)
         → glyph-index → 고유 슬롯 + 깊이층 → 눈꽃에 배치
```

각 글자 렌더 객체 최소 필드(필드명은 참고):
`{ entryId, date, graphemeIndex, sourceOffset, laneId, segmentId, slotId, glyph, x, y, angle, layer, opacity, fontSize, artVersion }`.

- **일기 기준 안정 키**는 `entry.id` + 그래픽 버전 + 월. `Math.random()` 렌더 호출 및 매번 배열 전체를 재섞는 작업 금지.
- `Intl.Segmenter` 지원 시 사용자에게 보이는 문자 단위(한글 음절/조합 문자/이모지)를 고려하고, 미지원 환경에는 안전한 fallback. 원문을 임의 단어로 재작성하지 않는다.
- **reading lane**은 서로 실제로 이어진 큰 줄기 또는 작은 가지의 인접 경로들로 이루어져야 하며, 단순 전역 y/x 정렬(현 `assignDiaryGlyphs` 방식)만으로 연결성을 보장했다고 주장하지 않는다.
- 일기 A의 단어 중간에 일기 B의 글자가 삽입되거나, 문장이 눈꽃 반대편으로 점프하면 실패. 길이가 부족하면 표현 가능한 **원문의 연속된 짧은 구절만** 보여준다.
- 독해 레이어에서는 **띄어쓰기/문장부호**를 고려해야 함. 공백은 글자 없이 적절한 간격으로 표현해도 되고, 문장부호는 실제 원문에 있는 것만 사용한다. 기존 `extractDiaryGlyphs`로 전부 제거하지 않는다.
- 읽기 방향이 갑자기 뒤집히지 않도록 경로의 접선을 보정하고, 뒤집힌 글자/문장 180° 회전을 피한다. 시안 축소 1×에선 형태, 확대 2~3.2×에선 **원문 연속 구절 일부**가 읽히게 한다.

### 4.2 표시할 텍스트 선택 [실험 초깃값]
- 긴 일기 전체를 담으려 하지 않는다. 일기당 8~16자 안팎의 **원문 연속 부분 문자열**을 우선 실험. 짧은 글은 짧게 유지.
- 긴 원문(300자 이상), 2~3글자 초단문, 한글·숫자·영문 혼용, 줄바꿈/문장부호, 공백만 입력(기존 저장 정책에 따라 거부) 케이스를 fixture에 포함.
- 별도 AI 요약/의역/가짜 문장 금지. 화면에 표시하지 않은 원문은 기존 일기 목록/상세에서 읽을 수 있어야 한다.
- 개인정보 보호를 위해 실제 사용자 텍스트가 포함된 그래픽을 자동으로 `toDataURL`, 외부 이미지/분석 로그 등으로 내보내지 않는다. Playwright 스냅샷에는 **가상 일기 데이터만** 주입한다.

### 4.3 슬롯 유지와 예외 규칙
- 새 날짜의 첫 일기는 새로 열린 상단 구간을 표현할 수 있다. 이전에 배치한 글자의 경로/슬롯/순서가 불필요하게 변하지 않는다.
- 같은 날짜 추가 일기는 **이미 열린 구간의 빈 자리나 보조층**에 채운다. 상단 성장 비율 변동 없음.
- 수정은 그 일기 문자와 독해 레이어를 갱신하는 것이 기본, 삭제는 그 일기 할당만 제거하는 것이 기본. 마지막 1편을 지운 날짜는 높이 축소가 선행하므로 상단 글자 리플로는 예외적으로 가능하되, 다른 기록이 통째로 사라지는 문제는 없어야 한다.
- 독해 레이어에 과도한 글자가 쌓여 경로를 덮거나 빈 공간이 부족해지면 밀도 제한/일부 발췌를 적용한다. 원문 자체를 삭제·변경하지 않는다.
- **중요 트레이드오프**: 무제한 일기 수, 모든 글자의 영구 고정, 그 달의 고정된 작은 실루엣, 아래→위 날짜 성장, 모든 글자의 판독성을 **모두 완벽히** 충족할 수는 없다. 초과분은 질감 레이어로 제한하거나 일부 미표시하고 원문 조회 경로를 보장한다. 이 한계를 구현 보고서에 명시한다.

## 5. 성장 및 미세 움직임 [확정 규칙 + 가정값]

### 5.1 성장
- 일반 월 기준 `ratio = min(writtenDays/15, 1)`; 단, **2026년 12월 특별 목표 미확정**이므로 실제 서비스의 완성 판정이나 일수는 변경 금지. Playground는 **일반 월 15일**의 검증용 fixture를 사용하고 그 사실을 내부 표시한다.
- 새로운 날짜의 저장: 아래에서 위로 새 영역이 약 0.8~1.2초 동안 결합되는 시안. 같은 날짜 추가: 성장 애니메이션 금지; 열린 부분에 부드럽게 글자만 결합.
- 숨겨진 윗부분 완성 실루엣 미리 노출 금지. 수평 마스크 때문에 접합부가 갑자기 잘려 보이면 경로별 성장 노출을 검토하되 높은 곳이 먼저 생기지 않도록.
- 0일 화면은 기존 홈 카피 정책을 유지; Playground에서는 비어 있는 작품만 표현.

### 5.2 모션
- 큰 줄기: 중심/접합 기준 ±0.2~0.5°, 8~12초(초깃값).
- 작은 가지: 자신의 뿌리 기준 ±0.5~1.1°, 6~10초(초깃값).
- 중심부 거의 정지, 각 가지 위상 분리. 각 글자 `requestAnimationFrame` 별 독립 애니메이션 금지; 가능한 **줄기/가지 그룹 transform** 단위로 처리.
- 깊이층 간 모션은 극소 차등 가능. 글자 간 원문 순서/읽기 경로가 흐트러져선 안 된다.
- 1× 정지 시안의 미적 완성도 승인 전, 모션을 덧붙여 부족한 조형을 가리지 않는다.
- 확대해서 읽는 동안 반복 모션 정지하는 방안을 먼저 실험(최종 정책은 시각 검수 후 결정). 실서비스 `GestureArtwork`의 핀치 동작 자체는 유지.
- `prefers-reduced-motion`, 앱 움직임 줄이기, 도감 축소판은 정적 렌더.

## 7. 기술 구조와 구현 요구

**이 저장소는 React 18 + TypeScript + Vite의 프로토타입**이다. 기존 코드/명세를 먼저 읽고 프로젝트 구조와 컴포넌트명은 충돌 없이 재사용한다. 다음은 제안 폴더 구조이며 현 코드 구조에 맞게 이름은 변경 가능.

```
src/graphics/snowflake/
  geometry.ts         # 6중 조형/연결성/줄기·가지 path, A/B 공용
  depth.ts            # front/mid/back 시각 깊이 매핑, A/B 공용
  readingLanes.ts     # 실제 연결 경로, 일기 단위 인접·순서 할당
  assignGlyphs.ts     # deterministic id+version seed, overflow 처리
  reveal.ts           # 날짜별 아래→위 성장, 기존 progress 규칙 연동
  studyFixtures.ts    # 개인 정보 없는 가상 일기 0/1/5/8/15일/동일 날짜 다수
  SnowflakeStudyArt.tsx # A/B variant="letters"|"connectors", 같은 엔진
src/dev/SnowflakeStudyPage.tsx # 개발 전용 UI, 배포 제외
```

**계산과 렌더 분리**
1. 순수 함수로 `geometry + reading lane + glyph assignment + progress + depth`를 만들고 **직렬화 가능한 결정적 배열**을 반환.
2. React/SVG는 결과를 그리는 역할만 하며, 매 렌더마다 전체 좌표계를 재난수 생성하거나 모든 노드에 개별 RAF를 만들지 않는다.
3. `entryId`와 slot/cluster를 안정 키로 사용. font-load가 완료된 뒤 글자 폭을 확인하되, 자동 측정 결과가 랜덤 배치 변경을 일으키지 않도록 비교 시 고정 서체·환경 사용.
4. SVG 기반 구현을 먼저 프로파일링. 장면당 글자가 매우 많거나 프레임 드롭이 심할 때만 Canvas/WebGL 대안을 **측정 결과와 함께 제안**, 허락 전 교체하지 않는다.
5. 개발 전용 페이지에 `data-testid`와 `data-variant`, `data-day-count`, `data-depth-layer`, `data-entry-id`, `data-lane-id` 등의 검사 표식을 부여하되 실제 기록 내용은 HTML 속성, 콘솔, 분석 로그로 복제하지 않는다.
6. 타입 체크 및 기존 `tests/logic.mjs`, `tests/glyph-layout.mjs`, 날짜·삭제 규칙을 깨지 말 것. 변경 내용은 구현 보고서에 명시.

**기술적 안전장치**
- 실제 일기/로그인 정보를 개발용 Fixture에 넣지 않는다.
- 클라이언트 스크립트·SVG 텍스트는 React의 기본 escaping으로 처리하며 사용자 문자열을 `dangerouslySetInnerHTML`/raw SVG/URL에 직접 주입하지 않는다.
- ARIA: 전체 작품을 `role="img"` + 월/작성일수로 요약, 장식 글자의 중복 스크린리더 노출 방지. 독해를 위한 전체 원문은 일기 상세에서 지원.
- 사용자 입력이 0자·1자·긴 줄바꿈·이모지·복합 한글일 때 화면 파손/NaN/무한 루프가 없어야 함.

## 8. 도구 구성: Playwright + MCP + 성능 프로파일 [개발 과정 필수]

**도구가 하는 일은 다름:** Playwright MCP는 Claude Code가 브라우저 화면을 직접 열어 **탐색/검토**하는 데 도움을 주고, `@playwright/test`는 코드에 남는 **재현 가능한 자동 테스트**를 만든다. Lighthouse와 Chrome Performance는 실제 렌더링 비용을 측정한다. 이 도구들을 쓴다고 시각적 완성도가 자동으로 올라가지는 않는다.

### 8.1 Claude Code의 브라우저 검토(선택: Playwright MCP)

Claude Code CLI가 현재 컴퓨터에서 동작한다면 아래 **공식 Playwright 명령**으로 MCP 서버 추가를 검토:

```bash
claude mcp add playwright npx @playwright/mcp@latest
```

- VS Code/Claude Code에 이미 Playwright 브라우저 도구가 연결되어 있으면 **중복 설치하지 말고** 활용.
- 목적: 실제 Vite 개발 서버 열기, 0·1·5·8·15일 전환, A/B 화면 스크린샷 찍기, 오류/레이아웃 검사.
- 저장소 자체의 자동 검증은 **MCP에 의존하지 않음**. CI는 Playwright Test 직접 실행.
- 환경마다 브라우저 실행 권한·설치 상태가 다를 수 있으니 실제 접속 성공을 확인하고 실패 사유를 보고.

참고: [Playwright MCP / Claude Code 공식 안내](https://playwright.dev/mcp/clients/claude-code).

### 8.2 재현 가능한 스크린샷·회귀 테스트(필수: `@playwright/test`)

```bash
npm install --save-dev @playwright/test
npx playwright install chromium
# 이후 npm run test:visual 등 프로젝트 스크립트로 고정
```

**기본 config 방향**
```ts
// playwright.config.ts — 프로젝트 실제 실행 포트에 맞게 최종 조정
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests/e2e',
  retries: process.env.CI ? 2 : 0,
  reporter: process.env.CI ? 'html' : 'list',
  use: {
    baseURL: 'http://127.0.0.1:4173',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
  projects: [
    { name: 'chromium-mobile', use: { ...devices['Pixel 7'] } },
    { name: 'chromium-desktop', use: { ...devices['Desktop Chrome'] } },
  ],
  webServer: {
    command: 'npm run dev -- --host 127.0.0.1 --port 4173 --strictPort',
    url: 'http://127.0.0.1:4173/__dev/snowflake-study',
    reuseExistingServer: !process.env.CI,
    timeout: 120_000,
  },
});
```

> 위 config는 가이드 코드: 실제 Vite 경로·버전·디바이스 이름·개발 라우팅은 설치 후 확인. CI/OS/폰트가 다른 환경의 픽셀 비교는 기준 이미지와 오탐 차이가 날 수 있으므로 **기준 브라우저/OS/서체 고정**. 처음 생성한 스냅샷은 사용자 디자인 검수 후 승인해서 저장한다.

**필수 테스트 매트릭스**

| 범주 | 케이스 | 검사 |
|---|---|---|
| 시각 캡처 | A/B × 0·1·5·8·15일 × 모바일 폭 320/375/430 | 정지 화면 PNG + viewport/폰트/seed 고정 |
| 상세 가독성 | A/B × 2×·3.2× × 혼합 문자/짧은/긴 일기 | 원문 구절 순서·간격·겹침과 스크린샷 |
| 깊이 | A/B × 15일 × 정지 | 앞/중/뒤 3층 존재, 형태 인지, 과한 광택 없음(사람 검토) |
| 성장 데이터 | 0→1→5→8→15, 동일 날짜 3편 | 신규 날짜만 높이 증가, 동일 날짜는 밀도만 증가 |
| 안정성 | 같은 fixture 재렌더·재진입·새 일기 추가·수정/삭제 | 기존 일기의 slotId/laneId 불필요한 변동 없음 |
| 모션 | 정지/재생/reduced motion | 스냅샷은 정적 상태로 고정, 자동화는 그룹 변환·정지 여부 검사 |
| 접근성 | 탭·키보드·확대 없이 보기·원문 일기 목록 | 포커스·이름·스크린리더 중복 억제·버튼 무추가 |
| 교차 브라우저 | Chromium 기본, WebKit/Firefox 스모크(환경 가능 시) | 렌더 오류·SVG 문자 배치·크기 차이 파악 |
| 모바일 제스처 | 핀치/팬/터치 취소/세로 스크롤 | 실제 Android/iOS WebView에서 최종 확인, 데스크톱 에뮬레이션만으로 검증 완료 처리 금지 |

**Playwright 테스트 작성 수칙**
- 테스트는 `data-testid`로 선택; 취약한 CSS 클래스·좌표 클릭 지양.
- 캡처 전에 폰트 로드 `await page.evaluate(() => document.fonts.ready)` 완료.
- 모션 OFF/시간 고정/동일 fixture seed/동일 zoom/reset 상태에서 비교. CSS 애니메이션뿐 아니라 SVG SMIL도 **명시적으로 정적 모드**를 제공해 결정적 스냅샷 작성.
- `expect(locator).toHaveScreenshot()` 활용, 작은 파티클 레이어의 안티앨리어싱 오탐을 허용하더라도 **눈꽃 전체가 달라지는 차이**를 `maxDiffPixels` 설정으로 숨기지 않음.
- 기준 스냅샷 자동 업데이트 금지. AI가 테스트 실패를 숨기기 위해 baseline을 무단 갱신하지 않는다.
- 실패 시 `trace.zip`, screenshot diff, console/pageerror, 실제/예상 이미지를 함께 보고.

참고: [Playwright Visual Comparisons](https://playwright.dev/docs/test-snapshots), [Playwright WebServer](https://playwright.dev/docs/test-webserver), [Trace Viewer](https://playwright.dev/docs/trace-viewer), [Playwright emulation](https://playwright.dev/docs/emulation).

### 8.3 브라우저 성능 측정/최적화(필수, 측정 불가 시 보고)

**도구**: Chrome DevTools Performance 트레이스(주요), Lighthouse(페이지 로딩/메인스레드 보조), Playwright 반복 진입·전환 타이밍 기록(기능 회귀). Lighthouse 점수가 높더라도 SVG 아트 애니메이션은 버벅일 수 있으므로 동작 테스트를 대체하지 않음.

**비교 조건**: 가상 15일치 일기, 2개 A/B 동시 렌더, 375×812, 동작 10초, CPU throttling 조건을 명시하여 같은 환경 3회 측정 후 중앙값 보고. 디자인 연구 단계에서는 개발 PC 결과와 Android 저사양 실기기 결과를 구분.

| 후보 예산 | 출발 목표 / 측정 설명 | 조치 |
|---|---|---|
| 60fps급 움직임 | 60Hz 장치 프레임 약 16.7ms, 주요 프레임에서 긴 끊김 최소화 | 변환 단위/리페인트/레이아웃을 트레이스로 확인 |
| 보급형 기기 하한 | 30fps 이상을 일단 검토 목표, 미달 시 모션 축소·정적 대안 | 실기기 결과에서 최종 목표 확정 |
| 프레임워크 재렌더 | 문구·컨트롤 변경에 아트의 전체 DOM 노드가 매 프레임 재생성되지 않음 | geometry/assignment 캐싱, 그룹 transform |
| DOM 규모 | 대량 글자로 수천 개 SVG text 노드가 생기면 프로파일 후 상한 검토 | 길이 발췌/밀도층 상한/정적 대안 |
| 메모리 | 페이지 진입·이탈 20회 반복에 캐시/RAF/리스너 누수 없음 | Heap snapshot/이벤트 핸들러 정리 |
| 로딩·상호작용 | Lighthouse 성능/접근성 결과와 실제 페이지 프로파일 제공 | 정량 점수 강제보다 이전 기준 대비 퇴행 설명 |

**중요**: 위 수치들은 계약상 성능 SLA가 아니라 **디자인 연구용 초기 예산**. 자동화가 실제 기기 속도와 배터리 소비를 보장하지 않는다. 60fps란 매 프레임 약 16.7ms의 예산이 있다는 뜻으로, 브라우저 처리 여유까지 고려하면 작업 부분의 비용은 더 적어야 한다.

참고: [web.dev Rendering Performance](https://web.dev/articles/rendering-performance/), [Lighthouse](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring).

## 9. 구현 단계 및 리뷰 게이트

### Gate 0 — Baseline/환경 검증
- 최신 브랜치 pull, `npm install`(락 파일 존재 여부 확인), 기존 타입/로직 테스트 실행.
- 현재 홈/도감/그래픽 화면의 변경 전 캡처를 **가상 fixture**로 보존.
- Playwright MCP 연결 시도 및 Playwright Test 준비; 설치 실패를 성공으로 보고 금지.

### Gate 1 — 정지 2.5D A/B (이번 요청의 우선 결과)
- 개발 전용 Playground, 공유 geometry/readingLane/depth, A/B 렌더 구현.
- 사용자에게 A/B 0·1·5·8·15일, 2×/3.2×, 장단점 요약 **스크린샷** 제출.
- 모션은 우선 OFF 기본값. 정지 상태의 시각적 승인 이전에 제품 `GraphicArtwork` 교체 금지.

### Gate 2 — 데이터 안정성/원문 판독
- 원문 구절 보존, 연결 경로, `entryId` 고정 배치, 같은 날 추가, 삭제/수정 회귀 테스트 통과.
- 수정 전에/후에 다른 entryId 좌표가 변했는지 snapshot/JSON diff 확인.

### Gate 3 — 모션·접근성·성능
- 승인 받은 시안에만 줄기/가지 미세 모션 적용. 정적 fallback/웹뷰 성능 비교.
- Playwright regression, Performance/Heap 기록, 실기기 검증 전에는 “모바일 제스처 검증 완료” 주장 금지.

### Gate 4 — 사용자 선택 후 제품 통합(별도 승인)
- 사용자 승인 A/B와 미적 피드백에 따라 실제 `GraphicArtwork` 교체 여부 결정.
- 배포 코드에 개발 페이지·임시 데이터·실험 컨트롤/임의 확장 기능이 섞이지 않았는지 감사.

## 10. 개발 결과물 제출 형식 (반드시 남길 것)

1. 어떤 브랜치/커밋에서 작업했는지, 바뀐 파일 목록.
2. A/B 0·1·5·8·15일 정지 PNG, 15일 1× 및 2×/3.2× 확대 화면, 모션 예시 짧은 녹화(가능한 경우).
3. 단위/Playwright/빌드/타입검사 로그(`PASS/FAIL/미실행` 명시). 설치 실패는 숨기지 않음.
4. Chrome 성능 기록: 브라우저·OS·CPU 조건·실행 기기·글자 수·FPS/프레임타임·메모리 비교, 실패 이유.
5. 디자인 의견에 필요한 관찰: 모서리/접합부 겹침, 글자 판독성과 좌우/상하 뭉침, A/B 연결 획의 장단점.
6. **Claude Code가 결정하지 말고 보고할 항목**: A/B 어느 안이 예쁜지에 대한 최종 판단, 최종 눈꽃 색/폰트, 그래픽 구조 변경, 실제 12월 목표, 실서비스 반영 시점.

## 11. 품질 수용 기준 / 자동화 가능한 것과 아닌 것

**자동화로 판단할 수 있는 것**
- A/B가 동일 fixture/글자 좌표·색·깊이층·seed로 렌더되고 연결 획의 유무만 다름.
- 같은 날짜에 2편 더 써도 성장 높이가 변하지 않음.
- 한 entryId의 문자가 reading lane에서 인접·원문 순서 유지, 다른 entryId가 중간에 끼지 않음.
- 새로운 일기 저장과 재진입에서 기존 entryId의 slotId/laneId가 안정적.
- 0일 미공개 영역 없음, 확대·축소 버튼이 실서비스에 생기지 않음.
- 정적 이미지 리그레션, reduced-motion 적용, 오류와 렌더 타이밍 비교.

**사람이 승인해야 하는 것**
- 작품이 2.5D처럼 자연스럽게 느껴지는지(과한 광택/입자 구름이 아닌지).
- 320/375px에서 눈꽃으로 인지되는지, 정지된 상태로 아름다운지.
- 2×/3.2×에서 진짜 글의 의미가 읽히는지, 시선이 글자 경로를 따라갈 수 있는지.
- B안 연결선이 형태를 돕는지, 그림 위 문자 오버레이처럼 보이게 만드는지.
- 모션이 정서적으로 적절하고 촌스럽지 않은지.

## 12. Claude Code에 넘길 작업 원칙

- **이 문서는 우선 Playground 구축을 요청하는 명세**다. 바로 제품 홈을 리디자인하거나 실서비스 코드를 갈아엎지 않는다.
- README/AGENTS와 기존 사용자 확정 정책을 읽고 충돌이 있으면 근거를 제시한다.
- 신규 문구·버튼·시각효과를 임의로 창작하지 않는다.
- A/B 디자인 실험은 독립 코드로 만들고, 사용자 승인 전 결과를 "완성된 눈꽃"이라고 부르지 않는다.
- 매 단계 변경 파일/테스트/시각자료를 제출하고, 사람이 눈으로 확인할 수 있는 정지 캡처를 반드시 제공한다.
