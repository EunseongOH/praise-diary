# 다정록 월간 작품 2단계 스냅샷 정책 v1.0

**정책 확정 2026-11-27 · 사용자 승인**  
**설계 명세만 반영 — 실제 snapshot 저장 코드·IndexedDB 보안·클라우드 배포는 아직 구현하지 않음.**  
관련: `37_Entry_Experience_Real_Artwork_Preview_v1.md`, `38_Backend_Privacy_Cost_Architecture_v0.1.md`, `40_Service_Wide_Data_Access_and_Backend_Decision_v0.2.md`.

## 1. 확정된 기본 규칙

매달 기록을 쌓아 **정식 `targetDays`** 에 도달한 경우에만, 작품의 실제 렌더러로부터 정지 상태의 압축 썸네일을 생성한다.

| 이벤트 | 스냅샷 | 도감 기본 표시 |
|---|---|---|
| 목표 일수 **최초 달성** (`beforeDays < targetDays && afterDays >= targetDays`) | `milestone` 1회 생성 | 그달이 끝나기 전에는 최초 완성 작품 표시 가능 |
| 그달의 기록 가능 기간 **마감** | 원천 내용이 달라졌을 때만 `final` 생성; 동일하면 `milestone` 참조 재사용 | 마감 후 **`final` 우선** |
| 목표 미달 월 | 완성 이미지 생성하지 않음 | 월명·기록일 수·미완성 상태만 표시 |
| 정식 목표 미확정 월 (`targetDays: null`) | 목표 달성으로 간주하거나 연구용 15일 프리뷰를 스냅샷으로 저장하지 않음 | 기존의 완료 상태를 임의로 표시하지 않음 |
| 작품 렌더러 미출시 월 (`planned`) | 스냅샷 없음 | 작품 준비 중 |
| 같은 월의 추가 기록 | 홈의 실제 렌더러는 계속 성장 | 목표 시점 스냅샷은 유지; **월 마감 시 최신 상태를 최종 스냅샷으로** |
| 월 마감 시 데이터 변경 없음 | 바이너리 중복 저장 없음 | 기존 `milestone`을 `final`의 별칭으로 참조 |

**원본 일기와 작품 썸네일의 역할:** 서버의 일기 원본만이 복구 가능한 정본이다. 썸네일은 **언제든 버리고 다시 만들 수 있는 파생 캐시**이며, 완성 시점의 텍스트 원문을 서버에 새로 복제하지 않는다.

## 2. '월 마감'의 정확한 시간

다정록의 사용자는 현재 월의 `오늘` 또는 `어제` 날짜로 일기를 새로 작성할 수 있으며, 날짜 경계 시각을 `boundaryHour`(0–4)로 설정할 수 있다. 기존 작성 화면은 시작할 때 정한 `entryDate`를 작성 도중 경계를 넘어도 유지한다.

**따라서 달력상 자정이나 다음 달 첫 순간에 강제로 최종화하지 않는다.**

- 해당 월 마지막 날짜(`YYYY-MM-lastDay`)가 더 이상 서비스의 `오늘`과 `어제`가 **둘 다 아니고**, 해당 날짜로 시작된 미완료 작성/동기화 작업도 없는 시점부터 `monthCloseEligible=true`.
- 예: 하루 경계가 **새벽 3시**인 2026년 12월의 경우, 2027년 1월 **2일 새벽 3시** 이후 12월 31일은 새 일기 작성 가능 날짜가 아니다. (기존 12월 31일 일기의 편집·삭제는 별개.)
- 자정 기준 설정이라면 2027년 1월 **2일 0시** 이후.
- 설정이 변하거나 기기 오프라인/시계 조작/다중 기기 사용이 있어도 안전하도록, **서버와 동기화된 현재 시각/기록 버전**을 기준으로 검증. 작성 중의 선택 날짜 보존 및 늦은 동기화도 고려.
- 백그라운드 Cron이나 기기 종료 시 강제 렌더링을 요구하지 않는다. 재진입 또는 도감/과거 월을 처음 열었을 때 **필요한 달만 lazy finalization**. 마감된 월이 많아도 일시에 모두 그리지 않는다.

**주의:** 편집·삭제는 과거 월에도 가능하므로 `final`이 원천 데이터가 절대 바뀌지 않는다는 뜻은 아니다. 원천 변경을 감지하면 해당 캐시를 무효화한다.

## 3. 이미지 생성 기준

- 실제 작품 렌더러(`artworkKey` 및 `rendererVersion`)에서 사용자의 `DiaryEntry` 본문, 고유 기록 날짜, 작성 순서로 생성한 정지 프레임만 허용한다.
- 성장·파티클 효과가 끝난 **정착 상태**를 캡처한다. 샘플 눈꽃/SVG 및 가상의 프리뷰 fixture를 사용자 스냅샷으로 쓰지 않는다.
- 모바일 도감 썸네일 초안: **320–384px 정사각형, WebP 품질 0.7–0.8**, 실제 한글 글리프가 있는 복잡한 눈꽃으로 실측해 품질/용량 최적값 확정. 목표 파일 크기 **20–60KB**는 검증 전 가정치.
- 프리뷰는 작게 표시하며 이미지를 탭해서 상세 작품을 열어야 할 때만 해당 월 원문을 내려받아 고해상도 그래픽을 다시 렌더링한다. 상세 보기 기능 자체를 막는 정책은 추후 UX 검수 가능.
- 도감에 여러 달이 있더라도 **보이는 타일에만** 캐시 이미지를 로딩하고, 원본 일기·Canvas 렌더러는 필요 시 가져온다. 이전 월의 미완성 작품을 완료 이미지로 오인시키지 않는다.

## 4. 저장 구조 및 중복 방지

작품별 스냅샷 메타데이터 예시 (아직 실제 DB 테이블 아님):

```ts
type SnapshotStage = 'milestone' | 'final';
type MonthlySnapshot = {
  ownerUid: string;               // only a scoped cache/metadata key; never trust client auth claims
  month: string;                  // YYYY-MM
  artworkKey: string;             // e.g., 2026-12/snowflake-v1
  rendererVersion: number;
  stage: SnapshotStage;
  completedAt?: string;           // milestone first-achieved event
  finalizedAt?: string;           // logical month closure event
  sourceRevision: number;         // server-authoritative per-month artwork-input revision
  sourceDayCount: number;
  mediaKey: string;               // device cache key or alias; NOT a public URL
  imageWidth: number;
  imageHeight: number;
  bytes: number;
  mimeType: 'image/webp' | 'image/png';
};
```

- 최초 달성 이벤트는 **`user + month + artworkKey`당 한 번**만 발행한다. 그 후 목표 이하로 감소했다 다시 증가해도 새로운 ‘첫 달성’ 이벤트를 반복 생성하지 않는다.
- 매월 최대 **서로 다른 2개 미디어 바이너리**(`milestone`, `final`)를 목표로 한다. 내용이 같으면 `final.mediaKey = milestone.mediaKey`로 중복 저장을 피한다.
- 캐시 무효화 판단은 `sourceRevision`, `artworkKey`/렌더러 버전, 실제 입력 변경을 기준으로 한다. **기록일 수만 비교해서는 안 된다.** 기존 본문 수정/같은 날짜 일기 추가/삭제로 작품 조형이 변할 수 있다.
- 현재 눈꽃의 그래픽 원천: 최소 `id`, `entryDate`, `createdAt`, `body`. 미래 작품은 해당 renderer의 의존 필드 선언을 활용한다. 반면 그래픽에 사용되지 않는 설정/회고만 변경했으면 불필요한 재렌더링을 막는다.
- 이미지 자체는 초기 **기기 로컬의 계정별 격리된 선택적 캐시**에만 저장하고, Firestore 문서에 Base64 이미지를 넣지 않는다. WebView 저장소 손실·기기 변경 시 캐시 미스 처리 및 원본 일기에서 재생성 가능하도록 한다.
- 위 로컬 캐시는 일기 본문 글리프에서 파생된 **민감한 데이터**다. 실제 영구 저장은 WebView XSS 위험, 이전 사용자 캐시 노출, 개인정보 삭제 후 잔존, 저장소 암호화·키 수명 관리의 보안 테스트가 완료되기 전에는 **도입하지 않고 메모리 캐시**를 기본으로 한다. 필요하면 삭제 가능한 단기 인덱스/메타데이터만 저장한다.
- 클라우드 간 기기 동기화가 꼭 필요해질 때만 **인증된 비공개 객체 저장소**(Cloud Storage 등)로 확장한다. 공개 URL, 공용 파일 버킷, 클라이언트가 임의 `uid`를 보낸 접근 금지. 이미지 업로드는 선택 사항이다.

## 5. 수정·삭제 후 스냅샷 정책 (데이터 보호가 우선)

| 변경 | 동작 |
|---|---|
| 목표 달성 후 **새 일기 추가** | `milestone`은 그 순간의 작품 기록으로 유지. `final`은 마감할 때 최신 입력으로 만듦 |
| 목표 달성 후 기존 일기 **내용 수정** | 이전 글자가 남아 있는 개인 이미지가 오래 노출되지 않도록 관련 캐시를 무효화. 현재 기록으로 재생성 가능하면 교체 |
| 목표 달성 후 **일기 삭제** | 해당 일기의 글자가 포함된 스냅샷을 즉시 삭제/무효화. 관련 `final`도 무효화 |
| 삭제로 기록일 수가 **목표 아래로 감소** | 기존 완성 썸네일 표시 중지. 일기 수는 최신 기록 기준. 필요하다면 최초 달성 메타데이터는 별도로 유지하되 삭제된 원문 파생 이미지는 유지하지 않음 |
| 마감 후 과거 기록을 수정/삭제 | 이전 `final`을 고정 역사 원본처럼 표시하지 않고 최신 실제 기록으로 **lazy 재생성**. 이는 새로운 월 마감 이벤트가 아니라 캐시 교체 |
| 모든 일기 삭제 또는 계정 탈퇴 | 본문, 회고, 원천 기반 모든 기기 스냅샷/캐시, 복구/동기화 메타데이터를 파기; 외부 백업 파기 기간 별도 고지 |

※ '마지막 날' 이미지가 보이더라도 사용자 삭제 요청으로 삭제된 글자가 다시 드러나면 안 된다. 이를 막을 수 없다면 해당 과거 월의 썸네일을 **표시하지 않는 쪽**이 안전하다.

## 6. UI 상태

- 현재 달에 목표 달성: 도감/홈에서 `milestone` 썸네일을 사용할 수 있지만 홈의 원본 기반 그래픽 성장은 계속된다.
- 과거 달의 `final` 유효: 도감 타일은 기본적으로 `final`을 보여준다.
- 과거 달의 `final`과 `milestone`이 동일: 하나의 이미지 바이너리만 유지한다.
- 과거 달 최종 스냅샷이 **아직 없는 경우**: '완성 이미지 준비 중'을 필요할 때 표시하고 최신 서버 일기를 가져와 재생성한다. 기존 사진과 닮은 임시 그래픽으로 대체하지 않는다.
- 현재 기록이 목표 미달: 완성 이미지 대신 기록 날짜 수/미완성 상태. 상세 화면에서도 존재하지 않는 완성 이미지를 만들지 않는다.
- 작품을 클릭해 상세 볼 때: 같은 달 기기 메모리 원문 캐시가 유효하면 재사용, 없으면 그달의 원문만 가져와 렌더링. 도감 전체 기간의 원문은 일괄 로딩하지 않는다.

## 7. 테스트 및 출시 게이트

1. 목표 달성 `14→15` 첫 1회만 milestone 발행, 같은 날 두 번째 기록은 재발행 없음.
2. `milestone`(15일) 후 추가(16·17·19일), 마감 뒤 19일 실제 최종 이미지가 도감 기본값.
3. 마감 시 원천 revision이 동일하면 바이너리 복제하지 않고 참조만 동일.
4. 12/31에 작성 가능한 마지막 날과 1/1의 '어제' 입력, 1/2의 자정/새벽 3시 마감, 작성 중 경계 통과, 오프라인 지연 동기화.
5. 메모리/저장소/OS 캐시 삭제 후 **사용자 자신의 원문**을 토대로 정확히 재생성. 기기 바뀌어도 복원.
6. 일기 1건 본문 수정, 당일 두 번째 기록, 개별 삭제, 월 기록 전체 삭제 후 오래된 글자가 이미지에 남지 않는지.
7. 서로 다른 2개 계정/2기기에서 이미지 캐시 키, 원본 요청, 작품 메타데이터가 혼합되지 않음.
8. 가상 프리뷰 기록은 `milestone`/`final` 스냅샷에 절대 사용하지 않음.
9. 작품 렌더러 버전 교체 후 구버전 썸네일 캐시가 안전하게 무효화되고 원본 기반 재생성됨.
10. 사용자 동작으로 수년치 도감을 스크롤해도 과거 원문 전량 다운로드·과거 작품 전체 동시 Canvas 계산을 하지 않음.

## 8. 백엔드 공급자와 독립된 계약

`SnapshotRepository`는 공급자 중립적 인터페이스다. Firebase·D1·Supabase 중 무엇을 선택해도 최초 완성 이벤트·월 마감 이벤트·유효성 검증·기기 캐시 재생성 정책을 유지한다. 이 스냅샷을 위해 서버에서 새 일기 원문을 분석하거나 이미지 렌더링하지 않는다.

**이번에 확정한 UX 정책과 실제 출시 준비 상태를 혼동하지 않는다:** 목표 일수 확정 여부, 기기 영구 캐시의 보안, 마감 후 데이터 변경 감지, 원본 DB 및 인증 연결은 별도 구현/검증이 필요하다. 12월 `targetDays:null`인 현 상태에서는 연구용 15일 스테이지를 정식 달성 스냅샷으로 생성하지 않는다.
