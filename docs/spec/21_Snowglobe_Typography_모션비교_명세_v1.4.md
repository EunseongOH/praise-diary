## 0. 목적, 소스 사실, 이번 결정의 성격

### 사용자가 요청한 경험 [사용자 방향 확정]

- 눈꽃의 각 줄기/가지에 감긴 **실제 일기 글자**가 중심축 주위를 아주 천천히 돌아, 뒤에 있던 글자가 앞으로 드러나고 앞에 있던 글자는 숨는다.
- 지금처럼 기계적으로 회전만 하지 않고 **스노우볼 속 반짝이는 눈가루처럼 작은 진동/부유와 은은한 반짝임**을 더한다.
- 글자들끼리 모여 나선과 눈꽃의 형태를 만들며, 멀리서는 상징물, 가까이에서는 내가 쓴 글자의 연속이 느껴져야 한다.
- 실제 앞뒤 위치/occlusion을 사용한다. **동일한 글자를 뒤에 복제해 가짜 그림자를 만들지 않는다.** 별·점·장식 입자를 새로 추가하지 않는다.

### 기존 Gate 2A 관찰 — Claude Code 보고값, 독립 검증 전

- 같은 축에 여러 기록을 S(세로 분할), R(반지름별 복수 트랙)로 누적하고, 고유 `entryDate` 수에 따라 아래에서 위로 성장하는 실험은 동작.
- S의 1일·3일 상태에서 같은 날짜 기록 +2의 정면 0° 차이가 0px인 결함, R안의 겹침/혼탁, 15일 기본 상태의 상단 빈 공간, 정지 화면의 약한 나선 실루엣 등 **기존 문제는 미해결**.
- Canvas2D 대비용 보고: S 8일 CPU4× 20.2fps, 긴 R 15일 +2 CPU4× 2.3fps(반복 오차 큰 환경); CPU1× 각 58.1fps, 48.1fps. 이 수치를 사실처럼 일반화하거나 이번 모션으로 해결됐다고 간주하지 않는다.
- Playwright MCP가 세션 등록 위치 문제로 안 보였다는 보고가 있었으므로 확인하되, 도구가 없어도 Playwright Test로 동일 검증을 진행한다.

**범위의 원칙:** 이 단계에서 기존 S/R 배치와 성장·가림·글자 순서·fixture를 그대로 고정한다. **변경 변수는 '모션 표현' 하나뿐**이다. 성능 불량과 S/R 구조 결함은 별도 트랙으로 기록하며, 새로운 효과로 가리지 않는다.

## 1. A/B/C 세 모션 시안 [동일한 기반·동일한 문장]

| 시안 | 회전 | 글자 부유 | 글자 밝기 반짝임 | 무엇을 평가하는가 |
|---|---|---|---|---|
| A — 회전만 | 기존 Gate 2A 축 회전 | 없음 | 없음 | 기준선(현재 사용자 평가: 단순 회전 느낌) |
| B — 회전 + 부유 | A와 속도·위상 동일 | 있음 | 없음 | 스노우볼의 유기적 움직임만으로 충분한가 |
| C — 회전 + 부유 + shimmer | A/B와 속도·위상 동일 | B와 동일한 움직임 | 있음 | 반짝임이 생동감을 주는가, 산만해지는가 |

**공통**: 동일한 원문/엔트리ID/작성일/나선 트랙/줄기 높이/카메라/글꼴/색상/성장 경계/가림/실제 글자 수/기준 각도/시간. A와 B의 차이는 부유만, B와 C의 차이는 반짝임만. 별 모양이나 별도 스파클 오브젝트를 추가하여 C에 유리하게 만들지 않는다.

- **모션만** 비교하므로 S와 R 중 어느 배치 방식을 채택할지 결정하지 않는다. 기본 판독 케이스는 **S 8일, 기본 문장, 추가 0**, 스트레스 케이스는 **R 15일, 긴 문장, 같은 날 +2**로 고정해 반드시 둘 다 비교.
- `prefers-reduced-motion: reduce`에서는 모든 자동 반복 효과를 OFF(기본 정지 각도와 문자 자체는 유지). 검사 페이지에서 강제로 재생할 수는 있어도 사용자 설정을 의도 없이 무시하지 않는다.
- 사용자가 화면에서 보는 속도와 오프라인 합성 영상의 부드러움을 동일시하지 않는다. 오프라인 영상에는 반드시 **'동일 모션식을 고정 시간으로 렌더한 합성. 실제 FPS 아님'**을 표시(영상 바깥 README/캡션).

## 2. 모션 수학·시안 출발값 [연구용, 최종 디자인 아님]

### 2.1 회전

- 축 주위 실제 3D 나선 위치와 앞뒤 가림은 Gate 2A 엔진의 현재 방식을 보존.
- **시안 회전 기본 1회전 20초**, 별도 느린 비교 24초. 이전 15초/24초와도 비교할 수 있게 한다. 20초는 디자인 초깃값이며 **실서비스 확정 속도가 아니다**.
- 두고 보는 기본 상태에서 한 방향으로만 계속 도는 나선. 눈꽃 전체가 카메라 중심으로 무한 회전하는 것이 아님.
- 각 시안의 같은 `t`에서는 회전 위상과 카메라가 완전히 같아야 함. 시간 원점과 기준 0°를 고정하여 재현 가능한 정지 프레임을 생성.

### 2.2 미세 부유 — B/C만

- 각 글자는 기존 나선의 좌표·원문 인덱스에 **결속**되어 있고, 나선에서 분리되거나 아래로 떨어지지 않는다. 작은 **연속 함수**의 오프셋만 추가.
- 첫 시안 출발값: **화면상 ±0.3~0.7 SVG-coordinate 단위** 정도, 원래 글자 크기의 대략 10% 미만을 목표. 시각적인 문장 연결성에 따라 더 낮춘 대안을 병행해도 된다. **화면 픽셀/Canvas DPR과 혼동 금지**. 크기 변경·확대 시 같은 상대 비율을 유지.
- 부유 주기: **3.5~7초 범위**, 글자 그룹별 결정적 위상. 개별 글자 단위 백색 잡음, `Math.random()` 매 프레임, 빠른 지터 금지.
- 이웃한 원문의 글자는 같은 흐름을 유지하도록 **같은 일기/나선 그룹의 저주파 이동 70~85% + 글자별 잔차 15~30%**를 연구 출발점으로 사용한다. 이 가중치 역시 승인값 아님.
- 구현 예: `offset(t) = sharedSin(t, strandId) * aShared + localSin(t, entryId:glyphIndex) * aLocal`. 시드/phase는 `entryId + graphemeIndex + artVersion`으로 결정. 순간 위치 변경이 아니라 주기적으로 연속한 움직임.
- 기존 `x,y,z` 회전 → 부유 오프셋(3D 물체 좌표계에서 계산) → 카메라 투영 → **깊이 검사·가림**의 순서가 일관되도록 설계. 원근상 앞/뒤가 뒤집히거나 노출 마스크 위로 튀어나오면 불합격.
- 부유는 같은 일기 독해용 인접 문자 사이의 평균 간격을 훼손하면 즉시 약화하는 제어 규칙을 둔다. **후행 글자가 앞 글자를 추월하는 이동 금지**.

### 2.3 은은한 문자 자체의 반짝임 — C만

- 효과는 **실제 사용자 원문 글자의 색 명도/불투명도의 아주 작은 변동**만 허용. 별/광원/점/파티클/하이라이트 획/블룸/블러/글로우/금속 질감 추가 금지.
- 첫 시안 출발값: **한 순간의 정면 가시 글자 약 3~6%에서만** 변화가 느껴지도록 하고, 밝기 차이는 **기본 대비 상대 +5~12% 수준**. 강한 흰색 점멸로 보이는 순간이 발생하지 않아야 함.
- 글자가 20자 미만인 1일 차 등에서는 비율만 엄격히 적용하면 0자가 되므로 **반짝임 0~1자** 허용. 글자가 몇 개 없어도 한꺼번에 다 번쩍이지 않게 한다.
- 광량 변화는 **1.8~3.2초의 부드러운 상승·하강 엔벨로프**를 사용하고, 나선별·글자별 타이밍을 시드로 분산. `sin²`/smoothstep처럼 시작과 끝이 매끄러운 함수. **불규칙한 1프레임 점멸 금지**.
- **앞면으로 보이는 글자**에서만 shimmer가 느껴진다. 뒷면 글자를 shimmer 때문에 새로 드러나게 하지 않는다. 기존 culling, 부유 이동 후의 가림 판정, 밝기 계산 순서를 테스트한다.
- 배경/전체 화면이 반짝이는 것이 아니라, 글자 일부만 생기 있게 밝아져야 함. B/C의 평상시 대비를 A와 동일하게 유지해 차이가 정확히 비교되도록 한다.
- 텍스트 색상·브랜드 팔레트는 미정. 기존 연구용 컬러만 재사용한다.

### 2.4 고정·일시정지·초기 상태

- `t=0`의 A/B/C 결과는 완전히 같을 필요는 없지만 **동일한 나선 기하·성장·원문**이어야 한다. 첫 화면 비교는 모션 OFF 기준 동일함을 검사한다.
- `pause`는 애니메이션 시간을 정지시켜, 재개 시 갑자기 위치가 점프하지 않아야 한다. 캡처에서 `t = 0, 2, 5, 10초` 등을 직접 지정할 수 있어야 한다.
- 브라우저 탭이 보이지 않는 경우 clock 정지/복귀 후보를 실험하되, 시간 기준과 프레임 제어의 차이를 README에 명시. 정지 탭에서 불필요한 계산 루프 실행 금지.
- 시각적으로 긴 글의 C가 지나치게 혼탁하면 반짝임/부유 정도를 낮추는 방식과 C 미채택을 **시안으로만** 비교, 최종 결정을 하지 않는다.

## 3. 성장 규칙·글자 데이터 불변 [Gate 2A 회귀 필수]

- 성장 높이 `writtenDays = unique(entryDate)`의 함수. fixture 일반 월은 15일 목표; 실제 2026-12 특별 목표는 미정.
- 0/1/3/5/8/15일과 같은 날짜 추가 0/2편을 Gate 2A와 같은 데이터로 검증. 모션 추가로 글자 수가 달라지거나 이미 보이던 글자가 다른 일기로 이동하면 실패.
- 새 날짜의 기록이 기존 아래쪽 실루엣 위로 성장하고, 같은 날짜에 추가해도 **높이는 변하지 않는다**. 처음 열린 영역의 **S 추가 기록 0px 변화 버그는 기존 결함으로 명시**; 모션 강도 증가로 버그를 '해결'한 것처럼 보고 금지.
- 0일에는 어떤 미래 글자/유령 실루엣도 보이지 않는다.
- 눈꽃 실루엣 클립과 나선 글자 occlusion은 다르다. **모든 시간 샘플/회전 각도에서 성장 경계 밖의 글자 전체가 나타나지 않도록** 검수하고, 반쯤 잘린 글자를 발생시키지 않는다.
- 짧은 일기의 불완전 회전은 원문을 반복해 3바퀴로 뻥튀기하지 않는다. 긴 일기 초과분도 임의 재작성/합성 금지. 실제 사용자 일기는 개발용 캡처에 사용하지 않는다.
- 수정·삭제·입력 순서 재정렬에서도 다른 엔트리의 기하 슬롯/원문 매핑/초기 모션 phase가 보존되는지 테스트.

## 4. 구현 방식 및 성능 — 이번 단계의 선행 제약

### 4.1 하지 말아야 하는 것

- 매 프레임 React state에 글자 배열 전체를 넣거나 component 1글자당 re-render를 발생시키는 것.
- 매 프레임 문자 레이아웃·측정·도형 기하·시드 계산·글리프 atlas를 다시 만드는 것.
- C의 반짝임을 위해 별도 Canvas 전체를 중첩하거나 글자를 복제하여 그리기 부하를 늘리는 것.
- 성능을 맞추기 위해 가시 글자 수/반지름/회전/occlusion을 줄이면서 기존 조건과 같다고 비교하는 것.
- CPU4× 수치를 실기기 저사양 Android의 실제 fps라고 단정하는 것.

### 4.2 권장 구조 [구현 후보, 프레임 프로파일 검증]

```
[Gate 2A의 고정 엔트리·트랙 데이터]
        → [진행·나선·글리프 메트릭·시드 캐시]
        → [하나의 presentation clock / render loop]
        → [기준 3D 좌표의 회전 + 연속 부유 + 앞뒤 가림]
        → [가시 글자에만 밝기 변조]
        → [Canvas2D 렌더]
```

- 개발용 별도 `SnowglobeMotionStudy`에서 **기존 engine을 공유하거나 래핑**하되 Gate 2A 원본 엔진/renderer를 임의 수정하지 않는다. 이 모션 비교에서 가능한 변경은 새 모듈과 개발 라우팅·테스트의 작은 확장만.
- 애니메이션 clock은 한 곳에서 수치적으로만 진행시키고, 글자별 배열·매핑은 데이터가 바뀔 때만 계산. 3개 시안을 나란히 렌더하는 경우 세 캔버스가 서로 중복 계산하는 부분은 캐시 공유 검토.
- Canvas2D glyph-cache 전략(프리렌더 문자 텍스처·고정 문자 계측)부터 시작하되 측정이 없으면 최적화 완료로 주장하지 않는다. WebGL2 도입은 **현재 범위에서 의무가 아니고**, 실기기 테스트 필요성과 구현 비용을 보고.
- **A/B/C 모두 같은 프레임 시계 기준**. 동기화되지 않은 별도 `requestAnimationFrame` 타이머로 비교 착시가 생기지 않도록 한다.
- 리소스/화면 밖 상태에서는 draw loop를 정리. 반복 진입·이탈 시 타이머 중복/메모리 증식 방지.

### 4.3 재현 가능한 성능 측정

- 조건: Chromium headless, viewport `375×812`, DPR 1, 동일 fixture 및 angle, 모션 A/B/C 각 10초 × 3회, CPU 1× 및 4×. **각 셋별 A/B/C 동일한 글자 수 및 가림 개수** 확인.
- 대표 2개 시나리오: `S / 8일 / 기본 / extra0`, `R / 15일 / long / extra2`. 가능하면 `S / 1일 / short / extra2` 엣지 케이스도.
- 매 시나리오별 `fps`, frame time `p50/p95`, `>33ms frame count`, Scripting/Layout/Paint, canvas draw 호출 횟수, glyph 메트릭/atlas 재생성 횟수, renderedGlyphCount, visibleGlyphCount, React render 횟수, 메모리 가능시를 JSON/표로 기록.
- **시안 효율 목표 [검증 가이드]**: B와 C에서 A 대비 같은 조건의 프레임 `p95` 악화가 가능하면 10% 이내; 목표 미달시 수치 그대로 보고. 성능이 낮아서 멈춰 보이는 상태를 모션 성공으로 판정하지 않는다.
- 위 지표를 만족하더라도 실제 Gate 2A 저사양 성능 목표(중간 30fps 근접, 긴 15fps 목표)가 이미 미달인 상황을 잊지 말고, **실서비스 최종 성능 승인으로 취급하지 않는다.**
- GPU가 없거나 GPU가 소프트웨어 에뮬레이션이면 환경을 명시. FPS 변동이 큰 경우 반복 표본 수·오차 범위 추가 및 정량 순위 보류.
- 짧은 MP4/GIF는 각도를 지정한 **오프라인 합성**일 수 있으나 실제 fps와 반드시 구분. Playwright 실제 브라우저에서 A/B/C 구동 성능도 따로 측정.
- 모바일 Android/iPhone 및 Apps-in-Toss WebView 실기기 미검증 상태 명시. 향후 기기 검증이 필요.

## 5. 개발용 UI, 제품 UX와 구분

- 신규 경로 제안: `/__dev/snowglobe-motion-study` (dev only, production bundle 제외 여부 실제 빌드/코드 구조로 확인).
- 개발용 패널 문구만 사용: `모션 비교`, `A 회전`, `B 회전·부유`, `C 회전·부유·반짝임`, `배치 방식`, `작성일 수`, `같은 날 추가 기록`, `문장 길이`, `회전`, `정지 각도`, `비교 시간`, `성장 경계 표시`. 더 필요한 디버그 파라미터는 URL/테스트 코드로만 허용.
- **개발 도구의 스위치와 시간 슬라이더는 실서비스에 복사 금지.** 실제 앱의 그래픽 상세에 `+/-`·배율·힌트 카피 추가 금지. 아트에는 카드/테두리/화려한 대시보드 UX가 없음.
- A/B/C 동일 데이터·시간·각도의 정지 비교를 한눈에 볼 수 있게 배치하되 좁은 모바일에서는 독립 캡처와 contact sheet 사용. 독해가 필요한 2×/3.2× 비교는 개발용 캡처/URL 파라미터 가능.
- 모션 감상용 기본 캡처에서는 성장 가이드/성능 로그 오버레이 OFF. 성능 보고서에 원문 일기 텍스트를 노출하지 않는다.

## 6. 자동 테스트와 시각적 결과물

### 6.1 통과/불합격 관찰 기준

1. A/B/C의 특정 시간이 같은 `entryId`, 원문 `graphemeIndex`, 나선 위치, front/back 가림을 유지하며 부유/밝기 요소 외의 차이가 없어야 한다.
2. 시간에 따른 B/C 글자 변위는 지정 상한 내이며, 나선에서 이탈/역주행/급격한 순간이동 없음. 같은 씨드/시간이면 스크린샷이 결정적으로 재생성됨.
3. C의 특정 글자 shimmer는 가려진 경우 화면에 드러나지 않음. 동시에 과반수 글자가 밝아지거나 빠른 번쩍임 없음.
4. 0일·1일·8일·15일, same-day+2, short/base/long/mixed에 대한 원문 순서/고유 날짜 성장/수정·삭제 정책 회귀 유지.
5. `prefers-reduced-motion`, pause, angle preset, 탭 비가시성에서 불필요한 모션 루프가 정지하고 재시작 시 갑작스러운 위상 점프 없음.
6. 영상은 시각 감상용이며 자동 테스트 통과가 시각적 승인과 같지 않음. A/B/C의 한글 가독성과 정지 미감은 사용자가 직접 결정.
7. 테스트 자체에서 새로운 구문 오류를 만들지 않을 것. 기존 `glyphLayout.ts:193` typecheck/build 실패 및 Windows `check:syntax` 경로 결함은 별도 표기, 실서비스 코드를 수정해 해결하지 않는다.

## 7. 작업 경계 및 Git 작업 보호
