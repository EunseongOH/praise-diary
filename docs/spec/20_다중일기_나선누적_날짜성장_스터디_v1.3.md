# 칭찬일기 — 다중 일기 나선 누적·날짜별 성장 스터디 구현 명세 v1.3

> 작성: 2026-11-21 · 문서 종류: **사용자가 검토할 설계 제안 + Claude Code 개발 전용 실험 명세**  
> 대상: `EunseongOH/praise-diary`, `feat/design-system-prototype`  
> **상태 표기**: `[확정]` = 사용자가 이미 결정한 정책/콘셉트, `[연구안]` = 이번 시안 비교의 구현 기준, `[보류]` = 검수 후 결정, `[실기기 검증]` = 브라우저 자동 테스트만으로 결론 내릴 수 없는 것.  
> 기존 `docs/spec/19_눈꽃_2.5D_AB_Playground_구현명세.md`를 대체하지 않는다. A/B 비교와 HelixStudy는 이전 실험이며, 이번 실험은 **한 줄기 안에 복수 일기가 누적되는 원리**를 다룬다.

## 0. 이번 작업의 핵심 질문

**한 편의 일기는 줄기나 가지를 감싸는 연속된 나선형 글자 띠를 형성한다. 한 줄기에는 여러 편의 일기가 서로 섞이지 않고 쌓일 수 있어야 한다.** 서로 다른 작성 날짜가 늘어나면 **눈꽃 전체**의 허용된 아래쪽 영역이 위로 확장되고, 같은 날짜에 추가로 쓴 글은 기존 높이를 유지하면서 그 안에 새로운 텍스트 나선을 형성한다.

- `[확정]` 하나의 줄기 = 하나의 일기라는 일대일 관계는 **금지**. 한 줄기에 여러 편을 담을 수 있어야 함.
- `[확정]` 글자들은 실제로 줄기의 둘레를 감고, 각각 줄기 축을 따라 천천히 회전한다. 앞→뒤로 가려지는 글자와 뒤→앞으로 나타나는 글자가 바뀌는 **진짜 공간적 깊이/가림**이 핵심. 복제 그림자, 평면 레이어만으로 대체 금지.
- `[확정]` 월간 성장 높이는 **서로 다른 `entryDate` 수**로 결정. 같은 날 몇 편을 써도 위쪽으로 자라지 않음.
- `[확정]` 짧은 문장을 억지로 반복하거나 가짜 문장을 생성해서 나선을 완성하지 않는다. 긴 문장 전체를 반드시 아트에서 읽게 하겠다는 약속도 하지 않는다. 원문 전체는 기존 일기 목록/상세에서 확인 가능.
- `[연구안]` 이번에는 **한 줄기만을 확대한 실험실**에서 복수 일기 누적/성장/회전을 검증한다. 이 실험은 눈꽃 여섯 줄기에 어떤 일기가 들어가는지 **최종 분배 정책의 확정이 아니다**.
- `[연구안]` 2D 화면에서 보이는 키네틱 타입 + 원통형 나선은 카메라가 고정된 **2.5D 표현**으로 설계. 실제 입체 좌표·앞뒤 가림이 있어야 하지만 전체 장면을 3D 조작 UI로 만들 필요는 없음.

## 1. 오해 방지: 전역 성장 vs 로컬 텍스트 적재

### 1.1 월간 성장 엔진(눈꽃 전체에 적용할 불변 규칙)

```text
해당 월 작성일의 고유 개수 U
         ↓
월별 목표 T(연구실 fixture에서는 T=15)
         ↓
허용되는 세로 영역: 눈꽃의 실제 하단 y_bottom에서 위로 증가
         ↓
허용 영역 안의 큰 줄기/작은 가지에서 새로운 글자 구조 활성화
```

- `U = number of distinct entryDate in month`, `progress = min(U/T, 1)` (T가 확정된 월만). **2026년 12월의 특별 목표 일수는 미정**, 연구용 15일을 실서비스 12월에 적용하지 말 것.
- 한 편의 일기가 반드시 다음 높이의 **맨 위에만** 배치될 필요는 없다. 새 일기에서 나온 글자가 현재 허용 영역의 나선 레인으로 분배될 수 있다. 단 **작성일이 새로 생겼을 때는 저장 직후 적어도 일부 새 글자가 보여야 하며**, 위쪽으로는 확실히 성장해야 한다.
- 전역 성장량은 **눈꽃 전체에 공유**된다. 예를 들어 서로 다른 8일의 기록이 있을 때 여섯 줄기는 모두 8일분의 해당 높이까지 활성화될 수 있지만, 그날의 일기 본문이 반드시 여섯 줄기에 복제되지는 않는다.
- 한 줄기는 여러 일기 조각을 담는 **공유된 숙주 축(host axis)**. 반대편 다른 줄기 또한 동일한 전역 성장 경계를 공유. 전체 실루엣을 미리 그려 놓거나 미래 부분에 흐린 가이드/글자 노출 금지.
- `0일`: 어떠한 눈꽃 구조나 미래 실루엣도 노출하지 않음. 단일 줄기 실험용 좌표선은 검수용 보조 가이드이며, 정식 아트 캡처에서는 OFF.

### 1.2 한 줄기 내부의 일기 누적 엔진

```text
공유된 줄기 축(축 위에 여러 편의 기록이 공존)
   ├─ 일기 A → 특정 축 구간을 감는 나선의 연속된 원문 부분
   ├─ 일기 B → 열린 축의 다른 구간 또는 인접한 나선 레인
   ├─ 일기 C → 아직 비어 있는 구간을 사용
   └─ 추가 일기 → 높이를 늘리지 않고 열린 구간의 빈 레인·층에만 배치
```

- **공유 축** 하나에 다수의 `entryId`가 존재할 수 있음. 각 `entryId`는 하나 이상의 **연결된 나선 조각**을 점유하며, 사용자 원문의 읽기 순서를 보존.
- 일기 간 글자들이 `A B A B` 식으로 번갈아 삽입되면 안 된다. 두 일기는 육안으로 서로 다른 구간 또는 인접 레인에 있어야 하며, 각 일기의 문장/구절은 각자 연속해서 흐른다.
- 축 구간(세로 높이)과 나선의 원주 위치/반지름을 함께 이용해 포화도를 관리. **새 텍스트가 추가돼도 기존 텍스트의 위치와 읽기 순서가 이유 없이 재배열되지 않게** 할 것.
- 같은 날짜의 복수 일기는 새 높이를 열지 않으면서, 같은 열린 부분에서 새로운 글자 구조가 생성되어야 함. 공간이 없는 경우 한 편 전체를 억지로 욱여넣지 않으며 **최소 가시 변화의 보장 가능성/한계**를 보고.

## 2. 배치 좌표 및 회전 모델 [연구안]

### 2.1 나선 객체

추천 데이터 구조(구체 필드명은 기존 코드에 맞춰 변경 가능):

```ts
// 개념 모델: 실제 타입/필드는 Claude Code가 기존 구조와 비교해 구현
interface HelixStrand {
  id: string;                   // stable strand key
  entryId: string;              // 작성 단위, lane과 1:1 아님
  entryDate: string;
  hostAxisId: string;           // 이번 실험 stem-01, 이후 6갈래·잔가지 확장
  zoneId: string;               // 허용된 높이의 구간/영역
  tStart: number;               // 축 시작 비율
  tEnd: number;                 // 축 끝 비율
  radius: number;
  turns: number;                // 짧은 문장에서는 부분 회전 허용
  phase0: number;               // 정해진 결정적 초기 위상
  rotationSpeed?: number;       // 검수용 모션 제어
  glyphs: Array<{ graphemeIndex: number; glyph: string; sourceOffset: number }>;
  artVersion: string;
}
```

한 글자 위치의 기준식(카메라 투영 이전의 로컬 3D 좌표):

```text
u = 글자 진행도 ∈ [0, 1]
θ(u,time) = phase0 + 2π × turns × u + ω × time
r = radius
localX = r × cos(θ)
localZ = r × sin(θ)       // 앞/뒤 깊이
localY = interpolate(axisStart, axisEnd, u)
```

- 나선은 실제로 중심축을 감는다. **같은 원문 글자를 앞·뒤로 복제해서 가짜 깊이를 만들지 않는다.**
- 글자는 한글 음절 등 사용자에게 보이는 **grapheme 단위**로 나누고 순서를 유지. 공백은 간격, 문장부호는 원문에 있는 것만 사용.
- 뒤쪽 글자는 축에 가리거나 시야에서 사라지고, 회전하며 앞으로 왔을 때 등장한다. 뒤쪽 반전 글자를 독해 가능한 문장처럼 노출하지 않는다. 옆면이 지나치게 얇아지면 페이드 또는 culling 하여 세로 막대 노이즈를 억제.
- 나선이 가려진다고 글자가 **삭제**되는 것은 아니다. 동일 각도로 돌아오면 동일한 원문 인덱스가 동일한 기하 위치를 가진다.
- 텍스트가 휘어지더라도 모든 글자를 과하게 비틀거나 거꾸로 보이게 하지 말 것. 독해 가능한 앞면 구간을 실험적으로 확인.

### 2.2 복수 일기의 구획 방식 비교 [A/B가 아닌 배치 설계 비교]

**배치안 S: 축 방향 분할(우선)**  
같은 줄기에서 A/B/C가 세로 구간을 나누어 점유한다. 원문은 각 구간을 나선형으로 감는다. 읽기 순서가 명료하고 충돌 관리가 쉬움. 단, 초기 열린 높이가 짧고 일기가 많으면 곧 포화됨.

**배치안 R: 작은 반지름 차이의 인접 레인(대안)**  
이미 열린 세로 영역 안에서 나선마다 살짝 다른 반지름/위상으로 들어간다. 같은 날짜 추가 일기를 보이게 할 가능성이 높지만, 글자 겹침·시각적 혼탁·뒤쪽 가림 복잡성이 커짐.

- **공통 요구**: 동일한 일기 데이터, 회전 속도, 문자 크기/색, 성장 경계로 S/R을 비교. 먼저 S의 독해·성장 문제를 보고, S가 포화되었을 때 R이 실제로 개선되는지 실험한다. 두 안 중 하나를 사용자가 승인하기 전 눈꽃 전체에 적용하지 않는다.
- 원문을 **나선으로 쓴다고 해서 줄기마다 동일한 내용을 반복 복제하지 않는다.** 하나의 일기가 분기해 여러 줄기에 배정되더라도 서로 다른 원문 구절을 배치하거나, 의도적 장식 반복의 여부를 별도 결정해야 한다.

## 3. 성장은 '날짜', 글자량은 '작성한 일기'로 분리 [최우선 불변조건]

| 입력 변화 | 전역 성장 높이 | 한 줄기의 나선 변화 | 검사 포인트 |
|---|---|---|---|
| 작성일 0→1일 | 증가 | 새 텍스트 최소 일부 등장 | 아무 것도 없는 화면처럼 보이지 않아야 함 |
| 새로운 날짜 첫 일기 | 한 단계 증가 | 이전 글자를 유지하며 새 일기 일부가 활성화 | 2일/3일 썼는데 4일째에만 보이면 실패 |
| 같은 날짜에 일기 1→2→3편 | 변하지 않음 | 열린 영역에 새로운 독립 나선/글자 조각 | 새 상단 영역·유령 그래픽 금지 |
| 기존 일기 본문 수정 | 변하지 않음 | 해당 일기 구절만 업데이트 | 다른 일기 레인의 불필요한 이동 방지 |
| 같은 날짜 여러 편 중 1편 삭제 | 변하지 않음 | 해당 일기의 글자만 제거 | 다른 일기의 위치 유지 |
| 해당 날짜 마지막 일기 삭제 | 한 단계 감소 | 새 성장 경계 위쪽은 비활성화, 필요 시 제한된 재배치 | 재배치가 있다면 정확히 보고·검증 |
| 목표 도달 후 추가 기록 | 증가하지 않음 | 현재 영역의 가용 슬롯에서 텍스트 누적 | 과밀 시 가독성을 지키고 미표시를 허용 |

### 3.1 작은 성장 단계에서의 가시성 문제

**중요한 물리적 한계:** 340 좌표계에서 전체 성장 높이를 15등분하면 처음 1일 구간은 매우 좁다. 같은 날 추가 일기까지 모두 **6~12자 문장**으로 읽히게 만들 수는 없다.

따라서 다음의 **우선순위**를 적용한다.

1. 위쪽 허용 영역을 넘기지 않는다(진짜 성장 규칙 우선).
2. 새 날짜 일기 저장 후 **적어도 하나 이상의 완전한 글자**가 열린 영역에 보이고 형태가 증가하는지를 검수 목표로 한다. 실제로 못 보이면 기능 결함을 기록한다.
3. 글자 전체를 반쯤 잘라서 노출하지 않는다. 성장 경계에서 글자별 완전 노출/비노출을 판정하고, 나타날 때 단위 글자 페이드 등 절제된 방식 사용.
4. 초기 낮은 성장 단계에서 읽을 수 있는 길이는 짧아도 괜찮다. **확대 후 연속 구절을 충분히 읽는 목표는 열린 영역에 용량이 생겼을 때 우선**.
5. 같은 날짜의 기록이 밀집해 정말 공간이 부족한 경우 사용자 원문은 삭제하지 않으며, 작품 안에 넣지 못한 글자는 기존 일기 목록에서 볼 수 있게 한다. 무작정 무한 레이어/글로우 추가 금지.

### 3.2 y 경계와 회전의 정합성

- 전역 y 기준 노출 구간 `revealTop = silhouetteBottom - silhouetteHeight × progress`.
- 나선의 **축 위치**를 기준으로 활성화하고, 카메라 12° 기울기·반지름 변화·회전 중 위치 이동을 고려한 **글자 경계/투영 면적**을 검사한다.
- 스터디에서 월간 y 경계를 시각화하는 가이드 라인을 개발 도구에서만 켜고 끌 수 있다. 그래픽 감상용 기본 캡처는 OFF.
- 도형 절단형 큰 clip으로 글자를 반만 잘라 놓는 대신, 글자별 가시/비가시 또는 글리프 전체가 경계 안으로 들어오는 상태를 사용한다.
- 글자가 회전하면서 축을 넘어가도 성장 경계 바깥에 예기치 않게 나타나지 않도록 **모든 시험 각도**에서 검사한다.

## 4. 일기 할당의 안정성과 초과 처리 [연구안]

### 4.1 결정적 할당

- `entryId`, `entryDate`, `createdAt`, `monthId`, `artVersion` 기반으로 정렬과 배치가 재현 가능해야 한다. 브라우저 재시작/다른 DPR에서 같은 원문은 같은 기하 객체를 만든다.
- 이후 일기를 추가할 때 이미 존재하는 `entryId`의 `hostAxisId / strandId / initial phase / 글자 인덱스`가 불필요하게 바뀌지 않게 한다.
- 새로운 일기로 전체 레인을 매번 균등 재분할하는 방식 금지. **안정 슬롯 또는 배정 기록(ledger)** 을 사용하는 방향 권장. 연구용 ledger는 데모 데이터만 갖고, 실데이터 영속 저장은 별도 백엔드 설계 전까지 하지 않는다.
- 삭제된 기록을 제거하고 남은 기록이 전부 앞으로 당겨지는 재배치가 발생하면 실패 사례로 기록한다. 날짜 마지막 글 삭제로 전역 성장이 줄어드는 것은 예외이므로 재배치 범위를 투명하게 보고.

### 4.2 긴/짧은 일기

- **짧은 일기:** 원문 길이보다 긴 나선을 강제로 만들지 않는다. 부분 회전을 허용하며 인접한 다른 일기의 나선이 시간이 지나며 모양을 채울 수 있게 한다. 사용자 문구를 반복할지 여부는 **이번 연구에서는 반복하지 않음**.
- **중간 일기:** 읽기 가능한 연속 6~12자 정도는 **충분한 공간이 생긴 뒤의 탐색 목표**. 첫날부터 보장하지 않는다.
- **긴 일기:** 표현 가능한 구간의 **연속된 원문 일부**만 사용하되 선택 구간·원문 인덱스를 안정적으로 보존. 원문 전체를 1개 줄기에 욱여넣지 않고, 최종 눈꽃에서는 인접한 가지/줄기에서 이어질 수 있도록 추후 별도 설계.
- **15일 + 동일 날짜 추가 2편 같은 스트레스 케이스:** 절대 모든 문자를 전부 읽히게 하려 하지 않는다. 실루엣과 화면 밀도를 우선 보존하고, 읽기 가능한 부분/질감 부분의 사용 범위를 보고한다.

## 6. 렌더링·성능: 이전 HelixStudy의 4.3fps 문제를 우선 해결

사용자가 받은 이전 Claude Code 보고: 중간 일기 CPU 4× 제한 15.4fps / 긴 일기 **4.3fps**. 주요 원인은 매 프레임 React가 글자별 transform과 SVG DOM 순서를 갱신해 Layout을 반복시키는 구조라는 보고임. 코드를 여기에서 직접 열어 검증한 수치는 아니며 **실험 보고값**으로 취급한다.

### 6.1 구현 지시

1. 기하 배치·엔트리 배정·텍스트 렌더·모션 clock을 분리. React state 업데이트를 60회/초로 발생시키지 않는다. 정지 또는 모션 시작 때 배치 데이터를 만들고, 프레임에는 회전 위상/투영만 갱신.
2. 글자마다 DOM 노드를 재정렬하는 렌더 경로를 **피할 수 있는지 실험**. 비교 후보는 `Canvas 2D + prerendered glyph cache`, `WebGL2 + glyph atlas/instanced quads` 등이며 특정 기술을 미학적 이유 없이 미리 확정하지 않는다. 가능한 최소 구현을 비교하고 도입·유지비용도 기록.
3. 실제 깊이 가림·뒤쪽 글자 숨김·원근 압축을 보장해야 하므로 단순 CSS 2D transform으로 입체 동작을 흉내만 내는 최적화는 허용하지 않는다. 단색 배경색으로 뒤쪽 글자를 가리는 테두리 방식은 임시 기술이며 제품 수준 occlusion으로 간주하지 않는다.
4. 프레임당 할당/가비지 컬렉션·SVG layout·글리프 texture 생성이 반복되지 않도록 캐시. 텍스트 변경 시에만 glyph atlas/문자 이미지 재구성.
5. 정지 화면은 애니메이션 없는 스냅샷으로 deterministic. reduced-motion에서는 자동 회전 중단. 화면 밖에서는 회전 clock 일시 정지 후보(검증 후 구현).
6. 색·광택·그림자를 임의로 높여 물리적 입체감을 속이지 않는다.

### 6.2 성능 수용 기준(목표, 합격 보장 아님)

- 동일한 headless Chromium/375×812/CPU 1×와 4×/10초×3회/같은 가상 원문과 **실제 그려진 글자 수를 함께** 보고한다.
- 기존 HelixStudy 값(중간 15.4fps, 긴 4.3fps at CPU4×)을 비교 기준으로 기록. FPS 외에 p95 frame time, 33ms 초과 프레임, Layout·Paint·Scripting, 눈에 보이는 문자 수 및 전체 생성 객체 수를 함께 기록.
- **권장 목표:** 중간 복수 일기 케이스에서 CPU4× 30fps 근접/이상, 긴 케이스에서도 15fps 이상 우선 목표. 충족하지 못하면 원인과 다음 선택지를 보고; 자동 회전을 저사양에서 정지시키는 fallback은 검토하되 임의로 상용 서비스 정책 확정 금지.
- 테스트를 위해 글자를 거의 렌더하지 않거나 나선/가림을 포기한 경우 성능 통과로 세지 않는다.
- Android/iOS 웹뷰 실기기 성능은 이 연구에서 **미검증**으로 남는다.

9. 짧은 글은 강제 반복하지 않으며, 긴 글에서 임의의 중간 글자 손실로 순서가 뒤죽박죽 되지 않음. 미표시 원문 전체는 원자료로 유지.

11. 375px 모바일·320px·430px 및 DPR 1·2로 화면이 경계 밖으로 넘치지 않음.
12. 기존 실험/실서비스 코드 비변경. 기존 typecheck/build 실패와 이번 변경의 신규 오류를 구분.
