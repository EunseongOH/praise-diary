## 1. 서비스 목적과 경험의 축

### 제품 의도 [확정]
하루의 일상에서 스스로 칭찬할 만한 일을 기록한다. 기록한 날짜가 누적됨에 따라 월간 그래픽이 **아래에서 위로 점차 형성**되며, 쓴 글자의 조각들이 그 그래픽에 더해진다. 시간이 흐른 뒤 과거의 칭찬일기를 무작위로 다시 꺼내 읽으면서 스스로 긍정적인 면을 발견하고 위로/격려를 얻는다. 매달 완성/미완성 그래픽 모두 도감에 보관한다.

### 원칙 [확정]
1. 수치형 진행 표시(큰 바/차트)를 주인공으로 삼지 않는다. 진행 일수는 작게 숫자로만 제시, 그래픽의 변화가 메인 피드백.
2. 일기 본문을 입력하기 전에 랜덤 회고 질문 2개를 제공하되, 질문 선택은 완전히 선택사항이다.
3. 내부 유형(성취/관계/용기 등), 상태 코드, 추첨 로직, 데이터 구조 등 사용자가 몰라도 되는 정보는 UI에 노출하지 않는다.
4. 사용자의 일기 원문은 사용자의 기록. 자동 생성 칭찬 문구보다 과거에 직접 쓴 문장을 그대로 꺼내 읽는 경험에 중점을 둔다.
5. 삭제 등 중요한 결과(데이터 삭제·작성일 감소)는 숨기지 않고 간결·명확하게 안내한다.

## 3. 날짜·기록·진행도 정책

### 기록 작성 [확정]
- 하루에 여러 편의 일기 작성 허용.
- 월간 진행도 = 해당 월 유효 일기의 **서로 다른 `entry_date` 개수**. 동일 날짜 여러 기록은 인정 1일만.
- 당일 이미 기록했더라도 추가 작성 CTA 유지.
- 작성 화면 기본 대상 날짜는 **서비스 기준 오늘**, 상단 날짜 선택으로 **서비스 기준 어제**로 변경할 수 있다. 직접 변경하지 않으면 오늘로 저장한다.
- **[확정]** 하루 경계 기본값은 KST **00:00(자정)**. 사용자는 S-01 설정에서 각자의 하루가 바뀌는 시각을 변경할 수 있다. 설정 시간 후보는 00:00/01:00/02:00/03:00/04:00 [제안, 미확정].
- **[확정]** 작성 중 날짜 경계가 지나도 입력과 선택한 `entry_date`를 보존하고 계속 작성할 수 있도록 저장 유예를 지원한다. 유예 종료 시점은 [보류]이며, 본문이 유실되지 않아야 한다.
- **[확정]** 일기 작성 화면 상단에 실제 저장 날짜(연·월·일)를 상시 노출하며 날짜를 바꾸거나 경계/설정 차이로 혼동할 때 짧은 안내를 제공한다. 토스트만으로 날짜를 전달하지 않는다.
- **[확정]** 날짜 경계 설정 변경은 기존 일기의 `entry_date`를 소급 변경하지 않는다. 입력 중인 초안의 선택 날짜도 자동 변경하지 않는다.
- **[확정]** 달력상 월이 바뀌더라도 `entry_date`가 전월이라면 **전월 그래픽**에 반영한다. 예: 1/1 01:00에 기본 자정이면 1/1, 경계를 03:00으로 설정한 사용자라면 서비스상 12/31.
- [제안] 지난 날짜에 대한 신규 작성은 지정된 '어제'까지만 허용. 기존 기록 수정은 별도 정책.

### 그래픽 변화 [확정]
- 새로운 날짜의 첫 일기 저장: 작성 인정일 +1, 그래픽이 아래에서 위로 새로운 영역을 얻는 성장 애니메이션.
- 해당 날짜의 추가 일기: 인정일 변동 없음, 기존 그래픽의 열린 영역에 글자들이 날아와 자리 잡음.
- 모든 유효 일기의 글자가 그래픽 구성에 기여한다. 화면 성능 때문에 일부만 표시하더라도 기록 반영은 재현 가능한 방식으로 구현.
- 15일 도달 시 그래픽 완성; 그 뒤에도 작성 가능하며 추가 글자는 그래픽에 반영(높이는 100% 유지).
- 해당 날짜 기록 중 일부 삭제: 남은 기록이 있으면 인정일 유지, 삭제한 글자만 그래픽에서 제거.
- 해당 날짜 마지막 일기 삭제: 인정일 -1, 그래픽 높이 감소. 삭제 전 영향 안내 필수.
- 완성 상태가 삭제로 해제되는 경우에는 그 변화까지 안내.

### 삭제 UX 카피 [확정]
- 작성일 감소가 발생할 때만 테마별 변형 안내.
  - 2026-12: **“12월의 눈꽃이 조금 녹아요.”**
  - 2027-01: **“1월의 붉은 양이 조금 작아져요.”**
- 동일 날짜에 다른 일기가 남아있는 삭제는 **“이 일기를 삭제하면 그래픽에서 해당 글자가 사라져요.”**를 사용하며 일수 감소를 언급하지 않음.
- 삭제는 복구 불가능함을 명확히 고지. [제안] 실제 복구 정책/소프트 삭제 보관기간은 기술·개인정보 정책에 따라 별도 결정.

## 5. H-01 월간 그래픽 홈

### 정보 위계 [확정]
- 월/테마명 → 대형 그래픽 → 작은 인정일 수 숫자 → 일기 작성 CTA → 글로벌 네비게이션.
- 사용자가 큰 프로그레스바/차트 없이 그래픽 높이만으로 진행을 이해하도록 디자인.
- CTA: 아직 작성 전 “오늘의 칭찬 남기기”, 같은 날 작성 후 “칭찬 하나 더 남기기”.
- 날짜별 상세 달력/일기 목록을 홈에서 과도하게 강조하지 않음 [제안].

### 상태
- 빈 상태(0일), 성장 중(1~목표-1일), 오늘 이미 작성, 완성 상태(목표일 이상), 그래픽 미공개, 그래픽 로딩 실패/네트워크 문제.
- 완성 직후에만 최초 특별 연출, 일반 재방문에서 매번 반복하지 않음 [제안].
- 홈 그래픽은 부유 Idle, 터치로 G-03 확대 감상. 홈에서 드래그 회전은 스크롤과 충돌하므로 후순위 [제안].

### 데이터
- 사용자, 서비스 기준 현재 날짜, 연월, 테마/에셋 버전, 인정일 수, 오늘 기록 수, 이번 달 총 기록 수, 그래픽용 텍스트 자료, 랜덤 시드/리비전.

## 6. D-01 칭찬일기 작성

### UI [확정]
- 상단 날짜 표시/변경(오늘·어제); 기본값 오늘.
- 본문 입력 **전** 랜덤 질문 **2개**를 노출. 질문 분류명은 사용자 UI에서 숨김.
- 질문은 서로 다른 유형에서 골라 중복 다양성을 줄임 [동의된 방향].
- 질문 선택 없이 바로 본문 작성 및 저장 가능.
- 한 질문을 선택하거나 취소할 수 있으며, 질문 선택은 본문 입력의 선행 조건이 아님.
- 다른 질문 보기 제공, 본문 입력 이후 질문 영역 접거나 재열기 [제안].
- 질문은 오늘/어제 대상 날짜에 맞춰 자연스럽게 문구 조정.

### 내부 질문 풀 [방향 확정, 수량 제안]
- 유형: 성취, 노력, 관계, 자기돌봄, 용기, 일상, 회복, 감사.
- 초기 질문 8유형 × 약 5개 = 약 40개 [제안]; 두 질문은 서로 다른 유형에서 선정.
- UI에서는 유형명/추첨 방식/질문 ID를 노출하지 않는다.

### 작성/입력/임시저장 [제안]
- 일기 본문 필수, 제목 선택·접힘, 본문 500자 상한(미확정).
- 자동 임시저장 및 이탈 시 복구; 저장 실패 시 입력 유지.
- 작성 중 날짜 변경 시 본문 유지, 대상 날짜만 변경.
- 서버는 `writing_started_at`, `entry_date`, `created_at`을 구분하고 경계 유예를 검증.
- 키보드 열림/스크롤/버튼 접근성 고려.

## 7. D-02 저장 완료/모션

- [확정] **Growth:** 새 인정 날짜의 첫 일기 → 아래→위 성장.
- [확정] **Enrichment:** 해당 날짜 추가 일기 → 열린 영역에 글자 합류, 높이 변화 없음.
- [확정] **Completion:** 최초 목표 도달 → 해당 월 특별 완성 연출.
- [제안] **Update:** 기존 일기 수정 → 글자 교체, 인정일 변화 없음.
- [확정] 12월 완성: 눈꽃 결정이 완성되어 반짝임. 1월 완성: 붉은 양이 완성되고 해가 떠오르는 분위기(구체 모션은 아직 제안).
- [제안] 글자 등장 → 지정 위치로 이동 → 자리 잡음. 완료 후 '다시 쓰기'·'그래픽 보기'·홈 이동.
- 저장 성공을 확인한 뒤에만 완료 연출. 렌더링 실패 시 정적 그래픽/완료 메시지 대체.
- 어제 입력에 의해 전월 그래픽이 변한 경우 전월 결과를 먼저 보여준 뒤 현재 월 홈으로 복귀.

## 8. L-01 꺼내보기 (상세는 `02_L01_꺼내보기_화면명세.md`)

### 목표 [확정된 의도]
과거에 직접 썼던 칭찬을 랜덤으로 다시 꺼내 읽으며 스스로 좋은 점을 발견하고 긍정적 자각/위로/격려로 연결되는 경험.

### 이용 조건과 잠금 화면 [확정 · 2026-11-21, v1.2 갱신]
- **활성 칭찬일기 10개를 최초 달성하면 '꺼내보기'가 영구 해제된다.** 해제 조건은 작성일 수가 아닌 개별 일기 수이며 같은 날짜의 여러 기록도 각각 1개로 계산. 이후 삭제로 10개 아래로 내려가도 잠기지 않는다. `users.letter_draw_unlocked_at`으로 최초 해제 이력을 보관한다. 전체 사용자 기록 삭제 시 이 해제 이력도 삭제한다.
- **최초 해제 이력이 없고** 활성 기록이 10개 미만이면 L-01-LOCK을 표시한다. 메인 CTA **'칭찬일기 남기러 가기'** → D-01. 해제 이력이 있으면 활성 기록이 0~9개라도 잠금으로 되돌리지 않는다.
- 잠금 화면 카피 초안(사용자 의도): **'나에게 남겼던 칭찬 중 하나를 되새겨볼 수 있는 공간이에요. 남겨진 칭찬이 많아지면 볼 수 있어요.'** 잠금 상태에서 분류명·복잡한 조건/알고리즘을 표시하지 않는다.
- 잠금 상태에서는 랜덤 CTA와 랜덤 결과를 노출하지 않으며, 홈으로 복귀 가능. **해제 이후 활성 기록 0개인 경우** ‘꺼낼 칭찬이 아직 없어요’와 작성 CTA를 표시한다. 1개면 해당 1개를 보여줄 수 있지만 다른 칭찬 뽑기는 숨긴다.
- 과거에 언급한 '기록 1개여도 랜덤 뽑기' 설계는 **폐기**한다.

### 구조 [제안, 위 이용 조건은 확정]
- L-01: 10개 미만이면 L-01-LOCK 안내; 해제 후에는 랜덤 추첨 메인과 '모든 기록 보기' 보조.
- L-02: 개별 일기 원문을 랜덤으로 꺼내 읽기. **같은 날의 여러 편도 서로 다른 후보 ID로 독립 추첨 대상 [확정].**
- L-03: 월별 그룹 일기 목록. 같은 날 여러 편은 개별 항목으로 표시.
- L-04: 개별 일기 상세, 수정·삭제(확정된 삭제 안내 정책 적용).
- [확정] 한 번 해제되면 이후 일기 삭제 후에도 재잠금하지 않음. [보류] 오래된 기록 우선 여부, 최근 중복 회피 길이, 꺼낸 편지 세션 보관 정책.
- [제안] 추첨은 `entry_id`별 균등 가중치를 기본으로 한다(정확한 가중치는 검토). 날짜 우선 추첨은 기본안에서 제외하여 같은 날의 여러 편도 독립 후보임을 유지.
- [제안] 10개 달성 직후 후보가 없어서 열 수 없는 상황을 피하도록, 모든 활성 일기를 우선 추첨 대상으로 하고 '과거' 우선 여부는 이후 결정.
- **[확정]** 홈 H-01에서 L-03 **모든 칭찬 기록 목록**에 독립적으로 접근할 수 있도록 한다. 꺼내보기 L-01은 열 편 잠금이지만 기존 기록 열람·수정·삭제는 잠금과 무관하다. **[제안]** 그래픽 하단에 낮은 위계의 명확한 텍스트 액션 ‘내가 남긴 칭찬 보기’ 배치. 길게 누르기는 발견성·접근성 문제로 단독 진입 수단으로 쓰지 않는다.

## 9. C-01 그래픽 도감 (상세는 `05_C01_그래픽도감_화면명세.md`)

- [확정] 완성·미완성 그래픽을 월별로 보관하고 언제든 감상. 미래 미공개 그래픽은 잠금 상태.
- [확정] 2열 카드형 도감: 월·테마명·그래픽·작은 작성일 수를 우선 보여주며 큰 진행바·실패 배지 사용 안 함.
- [제안] C-01 월별 목록 → C-02 그래픽 상세(완성/미완성/현재 진행) → 그달 기록 목록(L-03 필터). 잠금 카드는 H-03 재사용.
- [제안] 기록이 없는 지난달은 빈 보관함 상태, 미래 미공개는 잠금. ‘잠김’과 ‘그달 작성하지 않음’을 혼동하지 않음.
- [제안] G-02 지난달 그래픽 상세와 C-02 월별 상세는 동일 컴포넌트/동일 데이터 파이프라인 재사용.
- [제안] `year_month`, `asset_version`, `render_seed`, `written_days`, `target_days`, `month_entry_count`, `graphic_revision`, `theme_status` 등으로 표현; 글자는 실제 유효 일기에서 재현한다.
- [중요] 지난달 기록이 삭제/수정되면 도감 그래픽도 업데이트해야 하며, 잠금/원문 목록은 일기 데이터와 별개로 결합. 월말에 자동으로 상태를 불변 고정하면 안 됨.
- **[확정]** 미래 날짜/월에는 MVP에서 일기를 작성하지 않는다(오늘·어제만). 따라서 미래 월 미공개 그래픽을 이용한 작성 플로우는 MVP에서 제거한다. 실제 해당 월이 시작되기 전에 그래픽을 제작·배포해야 하는 운영 릴리스 조건은 별도 관리한다.
- [보류] 상세 화면 확대/회전·저장/공유, 시각 콘텐츠의 에셋 버전 보존 정책.

## 11. 데이터 모델의 최소 원칙

### User
`id`, 토스 익명 사용자 식별용 키(안전 저장/해시 등 검토), `created_at`, `onboarding_completed`, `timezone`, `status`, **`letter_draw_unlocked_at` (최초 10개 해제 시각, 이후 삭제로 취소하지 않음)**.

### DiaryEntries
`id`, `user_id`, `entry_date` (서비스 기준 기록 대상 날짜), `title?`, `body`, `created_at`, `updated_at`, `deleted_at?`.
**주의:** 동일 사용자·날짜 복수 기록 허용. `user_id+entry_date`에 UNIQUE 제약을 두면 안 됨. 활성 `entry_id`만 유일.

### DiaryDrafts [제안]
`id`, `user_id`, `entry_date`, `body`, `title?`, `writing_started_at`, `updated_at`, `status`.

### MonthCatalog / ThemeOptions [기본 자료구조 분리, 사용자 확장 의도 반영]
- `MonthCatalog`: `year_month`(PK), `target_days`, `availability_status`, `opens_at`, `closes_at?`. 월별 달성 조건과 공개/작성 상태를 관리.
- `ThemeOptions`: `theme_id`(PK), `year_month`(FK), `name`, `status`, `asset_version`, `render_config`, `growth_motion`, `addition_motion`, `completion_motion`, `deletion_motion`, `deletion_message`, `sort_order`. **한 달에 여러 후보가 연결될 수 있도록 `year_month`를 UNIQUE로 두지 않음.**
- **현재 MVP:** 2026-12 `snowflake`, 2027-01 `red_sheep_sun` 각 1종. 해당 월에 선택 가능한 후보가 1개면 선택 화면 없이 자동 지정.
- **향후 확장 의도 [확정]:** 한 달에 복수 테마 제공 가능; 첫 일기를 쓸 때 그래픽을 선택하는 흐름을 지원하는 아키텍처. 후보가 2개 이상인 경우에만 첫 저장 직전/첫 작성 진입에 선택 UI를 제공하는 정책은 [제안].

### UserMonthGraphicSelection [미래 확장 고려, 구현 세부는 제안]
`user_id`, `year_month`, `theme_id`, `selected_at`, `selection_source`, `render_seed`, `asset_version`.
사용자-월 조합은 최대 1개 선택 상태를 갖고(UNIQUE `user_id+year_month`), `theme_id`는 그 달 `ThemeOptions`에 속한 후보여야 한다. **선택은 첫 성공 저장과 함께 원자적으로 확정**하고, 첫 기록 이전 이탈/저장 실패에는 선택을 확정하지 않는 방식을 추천. 첫 저장 이후 선택 변경 허용 여부는 보류.

### GraphicIdeas [후보 제안 수집, 기능은 확정·세부 제약은 제안]
`id`, `user_id?`, `target_year_month`, `suggestion_text`, `created_at`, `status`, `reviewed_at?`. 미공개 월 카드에서 낮은 위계의 제안 CTA를 눌렀을 때만 입력. 필수 개인정보 추가 수집 없이 텍스트 제안 중심으로 설계. 입력 길이 제한·중복/스팸 방지·운영 검토는 추후 확정.

### MonthlyProgress [캐시/파생]
`user_id`, `year_month`, `written_days`, `completed_at?`, `render_revision`; 필요시 `theme_id`를 UserMonthGraphicSelection에서 조인한다. DB의 유효 기록들에서 DISTINCT entry_date로 계산. 삭제 후 재계산이 원칙.

### WritingPrompts
`id`, `category`, `text_today`, `text_yesterday`, `active`, `version`.

### LetterDrawHistory [제안]
`user_id`, `entry_id`, `drawn_at`; 개인 기록 원문은 분석 이벤트에 포함 금지.

### ReminderPreferences [검증 필요]
동의 여부/시각/타임존/마지막 발송일/해제 시각/동의 버전 등.

## 12. 그래픽 구현 설계 방향

- [제안] React WebView + Three.js/WebGL 기반 텍스트 파티클 2.5D 렌더러. CSS/SVG/Canvas는 정적/저사양 대체 및 초기 프로토타입.
- 선택된 그래픽 실루엣/벡터 에셋에서 파티클 배치 위치 생성. 위치는 사용자·월·**theme_id**·에셋 버전을 이용한 고정 시드로 재현. 한 달 다중 테마를 지원하기 때문에 월만으로 에셋을 결정하지 않음.
- 진행 높이(유효 날짜 수)와 텍스트 밀도/구성(총 기록 본문)을 별개 파라미터로 처리.
- 본문 전체를 공유용 그래픽에 자동 노출할 경우 프라이버시 위험. 사용자 지정 공유 옵션 없이는 개인정보가 누출되지 않도록 해야 함.
- [제안] 홈 진입 때마다 원문 전체를 내려받지 말고 그래픽 전용 가공 데이터 제공; 그래픽 로딩 실패 시 정적 폴백.
- [검증 필요] WebView 장치별 FPS, 메모리, 터치/스크롤 충돌, 렌더링 성능, TDS 호환성, 실제 모바일 사용성.
- Higgsfield는 필수 아님. 별도 영상은 연출 참고용으로 가능하지만 실시간 그래픽 구현을 대체하지 않음.

## 13. 공통 예외 처리·접근성

- 저장 성공 전 UI에서 성공으로 표시하지 않기; 실패 시 본문 유지·재시도 및 중복 저장 방지(`idempotencyKey`).
- 사용자별 하루 경계(기본 자정)를 넘은 경우 입력 날짜를 갑자기 바꾸지 않고 해당 작성 세션의 저장 유예를 검증.
- 월 교체·앱 포그라운드 복귀 시 기준일/테마 재검증.
- 삭제 시 남은 일기가 있는지 확인, 마지막 일기라면 일수 감소·그래픽 감소 안내.
- 그래픽 렌더 실패 시 정적 대체, 움직임 줄이기 설정 고려.
- 버튼으로 랜덤 뽑기 가능(동작을 흔들기/제스처에만 의존하지 않음), 긴 기록의 스크롤/큰 글씨/스크린리더 대응.
- UI에서 내부 타입/에러코드/질문 분류 노출 금지.

## 18. v1.6 통합 정책 변경 — 사용자 확정 (2026-11-21)

### 12월 특별 목표 — 날짜 미확정
- **[확정]** 2026년 12월에는 정규 15일과 다른 **특별 목표를 제공**한다. 정확한 일수는 실제 출시 시점에 맞춰 추후 결정한다.

- target_days는 월별 설정(`MonthCatalog`)으로 관리.

### 사용자별 하루 경계 — 기본 자정
- **[확정]** 기본값 KST 00:00. S-01에서 사용자가 하루가 바뀌는 시간을 변경 가능.
- **[제안]** 선택 가능 시각: 00/01/02/03/04시 정각. 너무 상세한 피커는 MVP에서 불필요할 수 있음.
- 서비스 날짜 함수: `effectiveDate = calendarDate(t - boundaryHour)`가 아니라 **시간이 설정 시각 전이면 캘린더 전날, 이후면 당일**(시간대 KST)로 정의. 설정이 00:00이면 언제나 캘린더 당일.
- 신규 작성 기본값은 설정상 오늘, 선택 가능 날짜는 설정상 오늘·어제. 화면에 실제 `YYYY년 M월 D일` 날짜를 항상 표시하고, 날짜 변경/새벽 혼동 시 짧게 안내.
- 작성 세션 중 경계 또는 설정이 바뀌어도 기존에 선택한 `entry_date`는 자동 변경하지 않음. 계속 작성 및 유예 저장은 유지(유예 종료시점 보류). 저장시 날짜 유효성·세션 유예 검증. 기존 저장된 일기 날짜를 소급 재계산하지 않음.
- `created_at`은 실제 저장 시각, `entry_date`는 고정 기록 날짜. 개인화된 경계 설정은 `Users.day_boundary_hour`(스키마 [제안])로 보관. 원문으로부터 월별 진행도를 재계산하지 말고 valid `entry_date` DISTINCT를 기준으로 계산.
