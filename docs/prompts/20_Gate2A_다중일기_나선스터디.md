## 2. 목적 / 하지 말아야 할 일

목적은 **한 줄기에 여러 일기가 독립적인 나선 구간으로 공존**하고, 월간 **서로 다른 작성일 수**가 증가할수록 **아래→위로 성장**하며, 같은 날의 추가 일기는 높이만 유지하는 원리를 검증하는 것입니다.

실서비스 `GraphicArtwork`, 홈, 도감, 작성/저장 화면 수정 금지. 기존 `/__dev/snowflake-study`, `/__dev/helix-study` 실험 결과 삭제·덮어쓰기 금지. 최종 눈꽃 6갈래 및 월별 목표일 정책을 바꾸지 마세요. 색상·글꼴·UX Writing을 임의로 브랜드 결정하지 마세요.

## 3. 구현 대상: 독립 개발 전용 페이지

- 개발 경로: `/__dev/multi-helix-study`
- 동일 축에 **3편 이상의 서로 다른 `entryId`**를 누적할 수 있는 엔진
- **배치 S:** 한 줄기의 세로 구간을 나누어 나선 배치
- **배치 R:** 허용된 구간 안의 서로 다른 반지름/위상/인접 레인으로 누적
- S/R 비교는 동일한 문구, 날짜 수, 성장 높이, 색/서체, 회전 시점으로 통제
- **글자 원문 그대로** 나선형으로 감고 실제 앞뒤 가림·회전 구현. 동일 글자 후경 복제 그림자 금지
- 엔트리별 stable key/슬롯/원문 글자 인덱스 유지. 새 기록으로 이전 기록 전체가 재배열되면 안 됨
- 0·1·3·5·8·15 고유 작성일과 마지막 날짜의 추가 일기 0/1/2편을 비교
- 짧은/긴/혼합 문자 dataset은 기존 19번 명세의 가상 일기 fixture를 재사용, 새 임의 문구 금지
- 15일은 **연구용** 목표. 실제 2026년 12월 목표는 변경하지 않음
- 새 날짜에는 기존 날짜와 비교해 **글자 하나 이상이 실제로 새로 보이도록** 노력하고, 불가능한 극한 포화 시 구현상 한계를 보고. 화면 위로 아직 열린 적 없는 부분 표시 금지
- 같은 날짜 추가에서는 성장 높이·revealTop이 변하지 않아야 함
- 성장 경계에서 글자를 반으로 자르지 말고 글자 단위로 노출
- `prefers-reduced-motion`에서 자동 회전하지 않음

## 4. 성능: 이전 실험의 병목을 피할 것

이전 보고에서 단일 줄기 긴 일기의 CPU 4× 조건은 **4.3fps**였습니다. 따라서 매 프레임 React state로 글자 위치와 SVG DOM 순서를 전부 교체하는 구조를 그대로 확대하지 마세요.

- 정적 글자 배치 계산과 프레임별 회전·투영을 분리하세요.
- 먼저 현재 병목을 측정하고 최소 변경 후보를 비교하세요. 필요한 경우 Canvas2D 글리프 캐시 / WebGL2 atlas 등 두 가지 경로 중 실현 가능한 후보를 소규모로 실험한 뒤 근거와 수치를 남기세요. 특정 렌더러의 도입이 과도하면 제약을 보고하세요.
- 실제 깊이 가림과 문장 일부의 가독성을 희생해 속도 수치만 높이지 마세요.
- 비교 조건: Chromium 375×812 / CPU 1×·4× / 10초 × 3회 / 동일 문구 및 **실제 표시 글자 수** 기록. FPS, 프레임 p95, 33ms 초과 프레임, SVG Layout·Paint·Scripting 등을 가능 범위에서 보고하세요.
- 중간 복수 일기 CPU4× **30fps 근접/이상**, 긴 케이스 **15fps 이상**은 **목표**이지 조용히 충족했다고 간주할 조건이 아닙니다. 미달이면 미달로 보고하고 최종 서비스에 적용하지 마세요.
- 실기기 앱인토스 WebView 성능은 검증 전까지 미검증으로 표시하세요.
